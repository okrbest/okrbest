## User Scenarios & Testing *(mandatory)*

### User Story 1 - 본부 생성과 부서 소속 지정 (Priority: P1)

팀 관리자가 부서/직위 관리 화면에서 본부를 새로 만들고, 기존·신규 부서를 특정 본부
소속으로 지정하거나 다른 본부로 이관한다. 부서 리스트는 본부별로 묶여 보이고,
본부에 속하지 않은 부서는 "미소속" 그룹으로 보인다.

**Why this priority**: 계층 구조의 뼈대. 본부를 만들고 부서를 연결할 수 없으면
나머지 기능(배정, 필터, 프로필 표시)이 모두 성립하지 않는다.

**Independent Test**: 관리 화면에서 본부 2개를 만들고 기존 부서를 각각 소속시킨 뒤,
부서 리스트가 본부별 그룹 + 미소속 그룹으로 표시되는 것만으로 독립 검증 가능.

**Acceptance Scenarios**:

1. **Given** 부서/직위 관리 화면, **When** 팀 관리자가 "본부 추가"로 이름을 입력해
   저장하면, **Then** 본부 리스트에 새 본부가 나타난다.
2. **Given** 본부가 1개 이상 존재, **When** 부서를 새로 만들며 소속 본부를 선택하면,
   **Then** 그 부서는 해당 본부 그룹 아래에 표시된다.
3. **Given** 무소속 부서가 존재, **When** 부서의 소속 본부를 A 본부로 변경(이관)하면,
   **Then** 부서가 A 본부 그룹으로 이동하고 기존 사용자 배정은 그대로 유지된다.
4. **Given** 부서 생성/수정 폼, **When** 소속 본부를 선택하지 않으면, **Then** 부서는
   무소속으로 저장되고 "미소속" 그룹에 표시된다(기존 부서 데이터도 동일하게 동작).

---

### User Story 2 - 본부 직속 인원 배정과 본부 단위 필터 (Priority: P2)

팀 관리자가 사용자를 부서뿐 아니라 본부에도 직접 배정한다(본부장·스태프 등 본부
직속 인원). 필터에서 본부를 선택하면 본부 직속 인원과 하위 부서 인원이 함께 보인다.

**Why this priority**: 계층이 실제 인사 배치를 반영하려면 본부 직속 배정이 필요하고,
본부 단위 조회는 관리자의 핵심 사용 흐름이다. P1 없이는 성립하지 않아 P2.

**Independent Test**: 본부 A(하위 부서 B 포함)를 만들고 사용자 1명은 본부 A 직속,
1명은 부서 B에 배정한 뒤, 필터에서 본부 A를 선택해 두 사용자가 모두 보이면 검증 완료.

**Acceptance Scenarios**:

1. **Given** 본부와 부서가 존재, **When** 사용자 배정 목록에서 소속 선택지를 열면,
   **Then** 본부(직속)와 부서가 그룹으로 구분되어 표시된다.
2. **Given** 사용자 배정 화면, **When** 사용자의 소속을 본부로 지정해 저장하면,
   **Then** 그 사용자는 본부 직속 인원으로 저장된다.
3. **Given** 본부 A에 직속 인원 1명과 하위 부서 B(인원 1명)가 존재, **When** 필터에서
   본부 A를 선택하면, **Then** 두 사용자가 모두 목록에 표시된다.
4. **Given** 필터에서 부서 B를 선택, **When** 조회하면, **Then** 부서 B 인원만 표시된다
   (본부 직속 인원은 제외).

---

### User Story 3 - 프로필 카드·계정 설정의 계층 표시 (Priority: P3)

팀 멤버가 동료의 프로필 카드를 열면 소속이 계층 형태로 보인다: 부서 배정자는
"본부명 > 부서명", 본부 직속은 "본부명", 무소속 부서는 "부서명"만.

**Why this priority**: 조회 전용 가시성 기능. P1·P2로 데이터가 쌓인 뒤에야 의미가
있으며, 없어도 관리 기능 자체는 동작한다.

**Independent Test**: 부서 배정·본부 직속·무소속 부서 배정 사용자 3명을 준비하고
각 프로필 카드의 소속 표기 형식만 확인하면 검증 완료.

**Acceptance Scenarios**:

1. **Given** 본부 A > 부서 B에 배정된 사용자, **When** 같은 팀 멤버가 프로필 카드를
   열면, **Then** 소속이 "A > B" 형식으로 표시된다.
2. **Given** 본부 A 직속 사용자, **When** 프로필 카드를 열면, **Then** "A"만 표시된다.
3. **Given** 무소속 부서 C에 배정된 사용자, **When** 프로필 카드를 열면, **Then**
   "C"만 표시된다(기존과 동일).

---

### Edge Cases

- 하위 부서 또는 직속 배정 사용자가 있는 본부를 삭제·비활성화하려 하면: 차단하고
  "하위 부서/직속 인원을 먼저 이관하라"는 안내를 보여준다.
- 비활성 본부는 부서의 소속 본부 선택지와 사용자 배정 선택지에 나타나지 않는다.
  (이미 그 본부에 소속된 부서·사용자의 기존 데이터는 유지된다.)
- 부서를 본부로, 본부를 부서로 바꾸는 유형 변경은 제공하지 않는다.
- 본부 아래에 본부를 두는 것(2단계 초과)은 저장 시 거부된다.
- 다른 팀(고객사)의 본부를 부서의 상위로 지정하려는 요청은 거부된다.
- 기존 데이터에 남아 있을 수 있는 'team' 유형 조직 단위: 새로 만들 수는 없고,
  조회 화면에서는 기존대로 표시만 유지된다.
- 저장 도중 팀을 전환해도 이전 팀의 응답이 새 팀 화면을 오염시키지 않는다(기존
  일괄 저장 가드와 동일 기준).

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 팀 관리자는 부서/직위 관리 화면에서 본부를 생성·이름 변경·활성/비활성
  전환·삭제할 수 있어야 한다(권한은 기존 부서 관리와 동일).
- **FR-002**: 본부는 상위 조직을 가질 수 없다(2단계 고정). 본부 아래에 본부를 두려는
  저장 요청은 거부되어야 한다.
- **FR-003**: 부서는 소속 본부를 선택하지 않거나(무소속), 같은 팀의 활성 본부 하나를
  소속으로 가질 수 있어야 한다. 기존 무소속 부서는 변경 없이 그대로 동작해야 한다.
- **FR-004**: 부서의 소속 본부 변경(이관) 시 해당 부서에 배정된 사용자들의 배정은
  그대로 유지되어야 한다.
- **FR-005**: 사용자의 주 소속은 본부 또는 부서 어느 쪽으로도 지정할 수 있어야 한다.
- **FR-006**: 하위 부서가 있거나 직속 배정 사용자가 있는 본부의 삭제·비활성화 요청은
  거부되고, 이관이 먼저 필요하다는 안내가 표시되어야 한다.
- **FR-007**: 부서 리스트는 본부별 그룹과 "미소속" 그룹으로 묶여 표시되어야 한다.
- **FR-008**: 사용자 배정의 소속 선택지는 본부(직속)와 부서를 구분해 그룹으로
  표시하되, 비활성 본부·부서는 선택지에서 제외해야 한다.
- **FR-009**: 필터에서 본부를 선택하면 본부 직속 인원과 하위 부서 인원이 모두
  조회되어야 하고, 부서를 선택하면 그 부서 인원만 조회되어야 한다.
- **FR-010**: 프로필 카드와 계정 설정의 소속 표시는 부서 배정 시 "본부명 > 부서명",
  본부 직속 시 "본부명", 무소속 부서 시 "부서명"이어야 한다. 열람 권한 범위는 기존
  소속 표시 기능과 동일하다.
- **FR-011**: 'team' 유형의 조직 단위는 신규 생성이 거부되어야 한다(고객사 구분은
  팀 단위가 담당). 기존 'team' 유형 데이터의 조회는 유지된다.
- **FR-012**: 본부 관련 생성·수정·삭제·이관은 기존 부서/직위 관리와 동일하게 변경
  이력(감사 로그)이 남아야 한다.
- **FR-013**: 다른 팀의 본부를 상위로 지정하는 요청, 존재하지 않는 본부를 상위로
  지정하는 요청은 거부되어야 한다.
- **FR-014**: 관리 화면의 신규 문구는 모두 다국어 리소스로 제공되어야 한다(한국어·
  영어, 기존 화면과 동일 기준).

### Key Entities

- **본부(Division)**: 부서의 상위 조직 단위. 팀(고객사) 내에서 이름을 가지며
  활성/비활성 상태를 갖는다. 상위 조직 없음(최상위).
- **부서(Department)**: 기존 조직 단위. 무소속이거나 하나의 본부에 소속된다.
- **사용자 조직 프로필**: 사용자별 주 소속(본부 또는 부서)과 주 직위. 기존 엔티티에
  본부 직속 배정 케이스가 추가된다.
- **팀(고객사)**: 본부·부서·직위·배정의 격리 경계. 모든 조직 단위는 한 팀에 속한다.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 팀 관리자가 본부 1개를 만들고 기존 부서 1개를 소속시키는 작업을 관리
  화면에서 1분 이내에 완료할 수 있다.
- **SC-002**: 기존 부서·직위·배정 데이터는 본 기능 배포 후 추가 작업 없이 그대로
  표시·동작한다(무소속 부서로 취급, 데이터 손실 0건).
- **SC-003**: 필터에서 본부를 선택했을 때 조회 결과가 본부 직속 + 하위 부서 인원의
  합집합과 정확히 일치한다(누락·중복 0건).
- **SC-004**: 하위 조직이나 직속 인원이 남아 있는 본부의 삭제 시도는 100% 차단되고,
  사용자에게 다음 조치(이관)가 안내된다.
- **SC-005**: 프로필 카드의 소속 표기가 세 케이스(부서 배정/본부 직속/무소속 부서)
  모두 정의된 형식과 일치한다.

## Assumptions

- 팀(Mattermost Team)이 고객사 격리 단위다. 별도 고객사 코드가 필요 없음을 확인했다.
- 계층은 v1에서 본부-부서 2단계로 고정하되, 향후 n단계 확장이 예정되어 있으므로
  깊이 제한은 데이터 구조가 아니라 저장 시 검증 규칙으로만 강제한다.
- 기존 부서 데이터는 전부 무소속(평면)이며, 마이그레이션 없이 "미소속" 그룹으로
  자연 수용한다.
- 본부 관리 권한은 기존 부서/직위 관리 권한(팀 관리자)과 동일하며 새 권한 체계를
  도입하지 않는다.
- 직위(Position) 체계는 이번 기능에서 변경하지 않는다.
- 조직 단위 'team' 유형은 실사용이 없는 잔재로 확인되어 신규 생성만 차단하고 별도
  데이터 정리는 이번 범위에서 제외한다.
