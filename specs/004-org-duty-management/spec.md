**Feature Branch**: `feat/permission` (사용자 지정 — 조직 관리 기능 전용 브랜치)

**Created**: 2026-07-30

**Status**: Draft

**Input**: User description: "부서/직위 관리에 직책(duty) 관리 기능 추가 — 직위(직급)와 별개로 직책(본부장·팀장·파트장 등)을 팀 단위로 정의하고 사용자에게 배정한다. 설계 합의사항: (1) 모델링은 독립 마스터+배정 — PositionDefinitions 테이블 재사용, Kind 컬럼('position'|'duty', DEFAULT 'position') 추가로 직위/직책 구분, 기존 행은 자동으로 직위 취급(무손실). (2) UserOrgProfiles에 PrimaryDutyID varchar(26) DEFAULT '' 컬럼 추가 — 사용자당 직책 1개(겸직은 추후 확장). DB 마이그레이션 1파일 발생(CODEOWNERS 보호 경로). (3) 검증: primary_duty_id는 같은 팀의 활성 kind='duty' 정의만, primary_position_id는 kind='position'만(교차 배정 차단). (4) 직책도 rank 정렬·active soft-delete·code 자동생성(prefix 'duty')·감사 로그 동일 적용, full_visibility는 직책에서 관리(직위 폼 미노출 — 구현 중 사용자 요구로 반전). (5) API: 기존 /positions CRUD에 kind 통과, /org-profile PUT에 primary_duty_id, summary 응답에 duty_name 추가 — 신규 엔드포인트 0. (6) 관리 UI(콘솔+팀 모달 공용 body): 직책 추가 버튼·직책 리스트 섹션(이름·정렬순서·상태·관리), 사용자 리스트 직책 select 컬럼, 필터에 직책 select, 일괄 지정에 직책 select('변경 안 함' 기본값). (7) 표시 형식: \"본부 > 부서 · 직책 · 직위\" 순 — 직책 미지정 시 항목 자체 생략(미지정 라벨 없음), 직위 미지정은 기존 \"직위 미지정\" 유지."

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 직책 정의 관리 (Priority: P1)

팀 관리자가 부서/직위 관리 화면에서 직위(부장·차장 등 직급)와 별개로 직책(본부장·
팀장·파트장 등 보직)을 만들고, 이름·정렬 순서를 관리하며, 더 이상 쓰지 않는 직책을
삭제(비활성)한다. 기존 직위 목록과 데이터는 그대로 유지된다.

**Why this priority**: 직책 마스터가 없으면 배정·표시가 성립하지 않는 기반 기능.

**Independent Test**: 관리 화면에서 직책 2개(팀장·본부장)를 만들고 직책 리스트에
정렬 순서대로 표시되는 것, 기존 직위 리스트가 영향 없음을 확인하는 것만으로 검증
가능.

**Acceptance Scenarios**:

1. **Given** 부서/직위 관리 화면, **When** 팀 관리자가 "직책 추가"로 이름과 정렬
   순서를 입력해 저장하면, **Then** 직책 리스트에 새 직책이 정렬 순서에 따라
   나타난다.
2. **Given** 직위와 직책이 각각 존재, **When** 관리 화면을 열면, **Then** 직위
   리스트와 직책 리스트가 별도 섹션으로 구분되어 표시되고 서로 섞이지 않는다.
3. **Given** 기존에 등록된 직위들, **When** 이 기능이 배포되면, **Then** 기존 직위
   데이터는 전부 직위 리스트에 그대로 남는다(변환·손실 없음).
4. **Given** 사용 중이지 않은 직책, **When** 삭제를 확인하면, **Then** 직책이
   리스트와 선택지에서 사라진다(비활성 처리).

---

### User Story 2 - 사용자 직책 배정·필터·일괄 지정 (Priority: P2)

팀 관리자가 사용자에게 직위와 별개로 직책을 1개 배정한다. 필터에서 직책을 선택해
해당 직책 보유자만 조회하고, 여러 사용자를 선택해 직책을 일괄 지정한다.

**Why this priority**: 직책 마스터(P1)를 실제 인사 데이터로 만드는 운영 핵심 흐름.

**Independent Test**: 사용자 A에게 직위=부장, 직책=팀장을 함께 배정하고 저장한 뒤,
직책 필터 "팀장"으로 A만 조회되면 검증 완료.

**Acceptance Scenarios**:

1. **Given** 사용자 리스트, **When** 사용자 행의 직책 선택지를 열면, **Then** 활성
   직책만 나열되고 직위 선택지와는 독립적으로 동작한다.
2. **Given** 사용자에게 직위가 이미 배정된 상태, **When** 직책을 추가로 배정해
   저장하면, **Then** 직위와 직책이 모두 유지된다(서로 덮어쓰지 않음).
3. **Given** 직책 선택지, **When** 직위를 직책 자리에 배정하려 하면(또는 그 반대),
   **Then** 시스템이 거부한다(교차 배정 차단).
4. **Given** 필터에서 직책 "팀장" 선택, **When** 조회하면, **Then** 팀장 직책
   보유자만 표시된다.
5. **Given** 사용자 여러 명 선택 + 일괄 지정에서 직책 선택, **When** 적용·저장하면,
   **Then** 선택된 전원에게 그 직책이 지정된다. 일괄 지정 기본값 "변경 안 함"은
   기존 직책을 건드리지 않는다.

---

### User Story 3 - 프로필 카드·계정 설정 직책 표시 (Priority: P3)

팀 멤버가 동료의 프로필 카드를 열면 소속·직책·직위가 "본부 > 부서 · 직책 · 직위"
순으로 보인다. 직책 미배정자는 직책 항목이 아예 표시되지 않는다(미지정 라벨 없음).
계정 설정에도 읽기 전용 직책 행이 추가된다.

**Why this priority**: 조회 전용 가시성. P1·P2 데이터가 있어야 의미 있음.

**Independent Test**: 직책 있는 사용자와 없는 사용자 프로필 카드의 표기 형식만
비교하면 검증 완료.

**Acceptance Scenarios**:

1. **Given** 본부 A > 부서 B, 직책=팀장, 직위=부장인 사용자, **When** 프로필 카드를
   열면, **Then** "A > B · 팀장 · 부장" 형식으로 표시된다.
2. **Given** 직책 미배정·직위 배정 사용자, **When** 프로필 카드를 열면, **Then**
   "부서 · 직위"만 표시되고 직책 자리는 생략된다(기존과 동일 형태).
3. **Given** 직책만 있고 직위는 미배정인 사용자, **When** 프로필 카드를 열면,
   **Then** "… · 팀장 · 직위 미지정"으로 표시된다(직위 미지정 라벨은 기존 유지).
4. **Given** 계정 설정 프로필 탭, **When** 직책이 배정된 사용자가 열면, **Then**
   읽기 전용 "직책" 행이 팀 관리자 관리 안내와 함께 표시된다.

---

### Edge Cases

- 사용자에게 배정된 직책을 삭제(비활성)하려 하면: 기존 직위 삭제와 동일한 정책을
  따른다(배정자가 있어도 비활성 가능, 이미 배정된 사용자의 표시는 유지되고 새 배정
  선택지에서만 제외). 단 이 정책이 직위와 다르게 동작해서는 안 된다.
- 비활성 직책은 배정·필터·일괄 지정 선택지에 나타나지 않는다.
- 직책과 직위 이름이 같아도(예: "본부장") 각자 리스트에서 독립적으로 존재할 수 있다.
- 정렬 순서가 같은 직책들은 이름순으로 정렬된다(직위와 동일 규칙).
- 배정 도중 팀 전환 시 이전 팀 응답이 새 화면을 오염시키지 않는다(기존 가드 기준).
- 보드 전체보기 권한은 직책 정의·수정 화면에서만 관리하고, 직위 화면에는
  나타나지 않는다.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 팀 관리자는 직책을 생성·이름 변경·정렬 순서 변경·활성/비활성 전환할
  수 있어야 한다(권한·감사 이력은 기존 직위 관리와 동일).
- **FR-002**: 직위와 직책은 하나의 관리 화면에서 별도 리스트로 구분 관리되어야
  하며, 기존 직위 데이터는 변환 없이 직위로 유지되어야 한다.
- **FR-003**: 사용자는 직위 1개와 직책 1개를 동시에 보유할 수 있어야 하며, 어느 한
  쪽의 배정·해제가 다른 쪽에 영향을 주지 않아야 한다.
- **FR-004**: 직위 자리에는 직위만, 직책 자리에는 직책만 배정할 수 있어야 한다
  (교차 배정 요청은 거부).
- **FR-005**: 배정·필터·일괄 지정의 직책 선택지에는 활성 직책만 표시되어야 한다.
- **FR-006**: 필터에서 직책을 선택하면 해당 직책 보유자만 조회되어야 하며, 기존
  소속·직위 필터와 조합(AND)되어야 한다.
- **FR-007**: 일괄 지정에 직책 항목이 추가되어야 하고, 기본값 "변경 안 함"은 대상
  사용자의 기존 직책을 유지해야 한다.
- **FR-008**: 프로필 카드·계정 설정의 표시는 "본부 > 부서 · 직책 · 직위" 순이어야
  한다. 직책 미배정 시 직책 항목은 생략(미지정 라벨 없음), 직위 미배정 시 기존
  "직위 미지정" 표기를 유지한다.
- **FR-009**: 직책 표시의 열람 권한 범위는 기존 소속·직위 표시와 동일해야 한다.
- **FR-010**: 직책의 생성·수정·비활성·배정 변경은 기존과 동일하게 변경 이력(감사
  로그)이 남아야 한다.
- **FR-011**: 관리 화면 신규 문구는 한국어·영어 다국어 리소스로 동시 제공되어야
  한다.
- **FR-012**: 보드 전체보기 권한 속성은 직책에서 관리되어야 하며(체크·해제 모두
  직책 화면), 직위 화면에는 노출되지 않아야 한다. 보드 전체보기 판정도 배정된
  직책 기준으로 동작해야 한다. (2026-07-30 사용자 요구로 직위→직책 이전)

### Key Entities

- **직책(Duty)**: 보직 명칭(본부장·팀장·파트장 등). 팀 단위 정의, 이름·정렬 순서·
  활성 상태 보유. 직위와 같은 성격의 마스터지만 용도(보직)가 다름.
- **직위(Position)**: 기존 직급 마스터(부장·차장 등). 변경 없음.
- **사용자 조직 프로필**: 기존 엔티티에 "주 직책" 1개가 추가됨. 주 소속·주 직위와
  독립.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 팀 관리자가 직책 1개를 만들어 사용자 1명에게 배정하는 작업을 관리
  화면에서 1분 이내에 완료할 수 있다.
- **SC-002**: 기존 직위·배정 데이터는 배포 후 추가 작업 없이 그대로 동작한다
  (변환·손실 0건).
- **SC-003**: 직위와 직책을 모두 가진 사용자의 프로필 표기가 정의된 순서("본부 >
  부서 · 직책 · 직위")와 100% 일치한다.
- **SC-004**: 직책 필터 조회 결과가 해당 직책 보유자 집합과 정확히 일치한다
  (누락·중복 0건).
- **SC-005**: 교차 배정 시도(직위↔직책 자리 바꿔치기)는 100% 거부된다.

## Assumptions

- 직책은 특정 조직 단위와 연결하지 않는 독립 명칭이다(브레인스토밍에서 "독립
  마스터 + 배정" 방식 확정). "인사팀의 팀장" 같은 조직 연계는 추후 확장.
- 사용자당 직책은 1개다. 겸직은 추후 확장 범위.
- 직책 관리 권한은 기존 부서/직위 관리 권한(팀 관리자)과 동일하다.
- 직책 비활성 정책은 기존 직위 비활성 정책과 동일하다(배정자 존재 시에도 비활성
  가능, 003의 본부 가드 같은 차단 없음).
- 003(본부-부서 계층) 기능이 먼저 반영되어 있다 — 표시 형식이 그 위에 얹힌다.
