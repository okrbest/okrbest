## User Scenarios & Testing *(mandatory)*

### User Story 1 - 비멤버 채널 게시물 열람 감사 (Priority: P1)

보안 담당자는 시스템 관리자 권한이나 신고/플래그 처리, 퍼머링크 등을 통해 사용자가 자신이 속하지 않은 채널의 게시물을 열람했을 때, 그 사실이 감사 로그에 남아 있어 사후에 확인할 수 있어야 한다.

**Why this priority**: 비멤버의 게시물 접근은 권한 상승(관리자 권한, 시스템 콘솔, 신고/플래그 처리 등) 경로로만 발생 가능한 민감한 이벤트이며, 이를 추적하지 못하면 컴플라이언스 감사·보안 사고 조사에서 핵심 증거가 누락된다. 이 기능의 핵심 가치이므로 최우선 순위다.

**Independent Test**: 채널 멤버가 아닌 사용자(또는 관리자 권한으로 접근하는 사용자)가 해당 채널의 게시물을 단건 조회 API로 열람했을 때, 감사 로그에 해당 접근이 "비멤버 접근"으로 표시되는 레코드가 생성되는지 확인하는 것으로 독립적으로 검증 가능하다.

**Acceptance Scenarios**:

1. **Given** 사용자가 채널 C의 멤버가 아니고 시스템 관리 권한으로 게시물을 조회하는 상황, **When** 사용자가 채널 C에 속한 게시물을 단건 조회하면, **Then** 감사 로그에 해당 게시물 접근 이벤트가 "채널 비멤버 접근" 표시와 함께 기록된다.
2. **Given** 사용자가 채널 C의 멤버인 상황, **When** 사용자가 채널 C의 게시물을 조회하면, **Then** 감사 로그에는 일반 접근으로만 기록되고 "채널 비멤버 접근" 표시는 남지 않는다.

---

### User Story 2 - 목록·스레드·검색 등 대량 조회에서의 비멤버 접근 감사 (Priority: P2)

보안 담당자는 게시물 단건 조회뿐 아니라, 채널별 게시물 목록, 스레드, 여러 게시물 ID 일괄 조회, 신고/플래그된 게시물 목록, 고정 게시물 목록, 게시물 편집 이력, 게시물 검색 등 다양한 조회 경로에서도 비멤버 채널 접근이 하나라도 포함되면 이를 감사 로그에서 확인할 수 있어야 한다.

**Why this priority**: 단건 조회만 감사하면 목록성·검색성 API를 통한 우회 접근이 추적 사각지대로 남는다. 다만 이는 User Story 1이 제공하는 감사 메커니즘을 여러 API 경로로 확장하는 것이므로 두 번째 우선순위다.

**Independent Test**: 여러 채널의 게시물을 한 번에 조회하는 API(예: 게시물 ID 목록 일괄 조회)에서 그중 하나라도 비멤버 채널의 게시물이 포함된 요청을 보냈을 때, 감사 로그에 "비멤버 접근 포함" 표시가 남는지 확인하는 것으로 독립적으로 검증 가능하다.

**Acceptance Scenarios**:

1. **Given** 사용자가 채널 A(멤버)와 채널 B(비멤버)의 게시물이 섞인 ID 목록으로 일괄 조회를 요청하는 상황, **When** 조회가 성공하면, **Then** 감사 로그에는 해당 요청이 "채널 비멤버 접근 포함"으로 표시된다.
2. **Given** 사용자가 자신이 멤버가 아닌 채널의 게시물 스레드를 조회하는 상황, **When** 스레드 조회가 성공하면, **Then** 감사 로그에 "채널 비멤버 접근"이 기록된다.
3. **Given** 사용자가 팀 내 게시물 검색을 수행했을 때 검색 결과에 비멤버 채널의 게시물이 포함되는 상황, **When** 검색이 성공하면, **Then** 감사 로그에 "채널 비멤버 접근"이 기록된다.

---

### User Story 3 - 비멤버 채널 파일 접근 감사 (Priority: P3)

보안 담당자는 사용자가 자신이 멤버가 아닌 채널에 첨부된 파일(원본 다운로드, 썸네일, 링크, 미리보기, 파일 정보, 파일 검색)에 접근했을 때 이를 감사 로그에서 확인할 수 있어야 한다.

**Why this priority**: 첨부 파일은 게시물 본문보다 더 민감한 콘텐츠(문서, 이미지 등)를 담을 수 있어 게시물 접근과 동등한 수준의 감사가 필요하지만, 발생 경로가 게시물 접근에 종속적인 경우가 많아 세 번째 우선순위로 둔다.

**Independent Test**: 비멤버 채널에 속한 파일을 원본·썸네일·미리보기 API로 다운로드했을 때, 감사 로그에 해당 파일 접근이 "채널 비멤버 접근"으로 표시되는지 확인하는 것으로 독립적으로 검증 가능하다.

**Acceptance Scenarios**:

1. **Given** 사용자가 채널 C의 멤버가 아니고 파일 접근이 허용된 상황(예: 관리자 권한), **When** 사용자가 채널 C에 속한 파일을 원본, 썸네일, 링크, 또는 미리보기로 조회하면, **Then** 감사 로그에 해당 파일 접근이 "채널 비멤버 접근"으로 기록된다.
2. **Given** 사용자가 파일 검색을 수행했을 때 결과에 비멤버 채널의 파일이 포함되는 상황, **When** 검색이 성공하면, **Then** 감사 로그에 "채널 비멤버 접근"이 기록된다.

---

### User Story 4 - 비멤버 채널 북마크 접근 감사 (Priority: P4)

보안 담당자는 사용자가 자신이 멤버가 아닌 채널의 북마크(생성·수정·삭제·목록 조회)에 접근했을 때 이를 감사 로그에서 확인할 수 있어야 한다.

**Why this priority**: 채널 북마크는 채널 내 중요 리소스·링크 모음을 드러낼 수 있어 감사 대상에 포함해야 하지만, 게시물·파일 접근 대비 민감도와 발생 빈도가 낮아 네 번째 우선순위로 둔다.

**Independent Test**: 비멤버 채널의 북마크 목록을 조회하거나 북마크를 수정·삭제했을 때, 감사 로그에 "채널 비멤버 접근" 표시가 남는지 확인하는 것으로 독립적으로 검증 가능하다.

**Acceptance Scenarios**:

1. **Given** 사용자가 채널 C의 멤버가 아닌 상황, **When** 사용자가 채널 C의 북마크 목록을 조회하면, **Then** 감사 로그에 "채널 비멤버 접근"이 기록된다.
2. **Given** 사용자가 비멤버 채널의 북마크를 생성·수정·삭제하면, **Then** 감사 로그에 "채널 비멤버 접근"이 기록된다.

---

### User Story 5 - 링크 미리보기·웹소켓 퍼머링크를 통한 비멤버 접근 감사 (Priority: P5)

보안 담당자는 사용자가 게시물을 작성할 때 첨부되는 링크 미리보기(퍼머링크 프리뷰)나, 웹소켓을 통해 실시간으로 전달되는 퍼머링크 게시물 미리보기, 알림(푸시/이메일) 생성 과정이 비멤버 채널의 게시물을 참조하는 경우에도 이를 감사 로그에서 구분해 확인할 수 있어야 한다.

**Why this priority**: 미리보기·알림 경로는 사용자가 명시적으로 "조회"를 요청하지 않아도 발생할 수 있는 간접 노출 경로로, 감사 커버리지의 완결성을 위해 필요하지만 다른 스토리 대비 발생 빈도와 위험도가 낮아 마지막 우선순위로 둔다.

**Independent Test**: 비멤버 채널의 게시물을 링크로 참조하는 퍼머링크를 포함한 게시물을 생성했을 때, 감사 로그에 해당 미리보기가 "비멤버 채널 미리보기 접근"으로 별도 표시되는지 확인하는 것으로 독립적으로 검증 가능하다.

**Acceptance Scenarios**:

1. **Given** 사용자가 비멤버 채널의 게시물을 가리키는 퍼머링크를 포함해 새 게시물을 작성하는 상황, **When** 게시물이 생성되고 링크 미리보기가 첨부되면, **Then** 감사 로그에 해당 미리보기 게시물 ID와 함께 "비멤버 채널 미리보기 접근"이 기록된다.
2. **Given** 웹소켓을 통해 비멤버 채널의 게시물이 퍼머링크 미리보기로 사용자에게 전달되는 상황, **When** 해당 이벤트가 발생하면, **Then** 감사 로그에 이 웹소켓 이벤트도 "비멤버 접근"으로 기록된다.

---

### Edge Cases

- 사용자가 과거에는 채널 멤버였다가 탈퇴한 뒤, 자신이 작성했던 게시물이나 스레드를 다시 조회하는 경우 → 현재 멤버십 기준으로 비멤버 접근으로 기록되어야 한다.
- 공개(Public) 채널이라 브라우징 권한상 조회 자체는 허용되지만 실제 채널 멤버는 아닌 경우 → 접근은 허용하되 감사 로그에는 비멤버 접근으로 기록되어야 한다(권한 허용 여부와 감사 기록 여부는 별개).
- 시스템 관리자(`manage_system`) 권한으로 임의 채널의 게시물·파일에 접근하는 경우 → 권한상 접근은 허용되지만, 실제 채널 멤버가 아니라면 마찬가지로 비멤버 접근으로 기록되어야 한다.
- 여러 게시물을 한 번에 조회하는 요청에서 일부만 비멤버 채널에 속한 경우 → 요청 전체가 "비멤버 접근 포함"으로 한 번 표시되며, 어떤 개별 게시물이 문제였는지까지 낱낱이 구분하지는 않는다(요청 단위 감사).
- 채널이나 파일, 북마크가 삭제되었거나 찾을 수 없는 경우 → 기존 오류 처리(404/403 등)를 그대로 따르며, 비멤버 접근 감사는 실제로 컨텐츠가 반환된 경우에만 남긴다.
- 북마크가 가리키는 채널 자체가 비멤버 채널인 경우(북마크 목록 조회 시) → 북마크 목록 응답이 반환되면 감사 로그에 비멤버 접근으로 기록되어야 한다.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 시스템은 사용자가 자신이 멤버가 아닌 채널에 속한 게시물을 조회(단건 조회)할 때, 해당 접근을 감사 로그에 "채널 비멤버 접근"으로 표시해 기록해야 한다.
- **FR-002**: 시스템은 채널별 게시물 목록 조회, 마지막 읽지 않은 지점 기준 조회, 게시물 스레드 조회, 게시물 ID 일괄 조회, 신고/플래그된 게시물 목록 조회, 고정 게시물 목록 조회, 게시물 편집 이력 조회, 게시물 검색 등 게시물을 반환하는 모든 조회 API에서, 응답에 포함된 게시물 중 하나라도 비멤버 채널에 속하면 해당 요청을 "채널 비멤버 접근"으로 감사 로그에 기록해야 한다.
- **FR-003**: 시스템은 파일 원본 다운로드, 썸네일, 링크, 미리보기, 파일 정보 조회, 파일 검색 등 파일을 반환하는 모든 API에서, 반환된 파일이 비멤버 채널에 속하면 해당 요청을 "채널 비멤버 접근"으로 감사 로그에 기록해야 한다.
- **FR-004**: 시스템은 채널 북마크 생성·수정·삭제·목록 조회 API에서, 대상 채널이 비멤버 채널이면 해당 요청을 "채널 비멤버 접근"으로 감사 로그에 기록해야 한다.
- **FR-005**: 시스템은 게시물 생성·임시(에페메럴) 게시물 생성 시 첨부되는 링크 미리보기(퍼머링크 프리뷰)가 비멤버 채널의 게시물을 참조하는 경우, 이를 "비멤버 채널 미리보기 접근"으로 구분해 감사 로그에 기록하고 해당 미리보기 게시물 ID를 함께 남겨야 한다.
- **FR-006**: 시스템은 웹소켓을 통해 전달되는 퍼머링크 게시물 미리보기 이벤트에서도, 참조된 게시물이 비멤버 채널에 속하면 이를 감사 로그에 기록해야 한다.
- **FR-007**: 시스템은 각 감사 이벤트에 접근 대상 식별자(채널 ID, 게시물 ID 또는 게시물 ID 목록, 파일 ID, 북마크 ID 중 해당하는 것)를 함께 기록해, 사후 조사 시 어떤 채널·컨텐츠가 비멤버 상태로 접근되었는지 특정할 수 있어야 한다.
- **FR-008**: "비멤버 접근" 표시는 접근이 허용되었는지(권한상 성공했는지) 여부와 무관하게, 실제로 컨텐츠(게시물·파일·북마크)가 조회자에게 반환된 경우에만 기록되어야 한다 — 권한 거부(403/404)로 접근이 실패한 요청은 별도의 비멤버 접근 감사 대상이 아니다(기존 실패 감사 기록 체계를 따른다).
- **FR-009**: 이 감사 기록은 okrbest가 이미 사용 중인 기존 감사 로그 인프라(감사 이벤트·레벨·파라미터 체계)를 그대로 재사용해야 하며, 별도의 저장소나 조회 화면을 신설하지 않는다.
- **FR-010**: 채널 멤버가 자신이 속한 채널의 게시물·파일·북마크에 접근하는 일반적인 흐름에는 "비멤버 접근" 표시가 추가되지 않아야 하며, 기존 감사 로그의 볼륨·형식에 변화를 주지 않아야 한다.

### Key Entities

- **감사 레코드(Audit Record)**: 기존 okrbest 감사 로그 시스템의 이벤트 단위. 이 기능은 여기에 "채널 비멤버 접근 여부"를 나타내는 파라미터를 추가로 덧붙인다.
- **게시물(Post)**: 조회 대상. 소속 채널 ID를 통해 조회자의 채널 멤버십과 대조된다.
- **파일(File)**: 게시물에 첨부되어 채널에 속하는 조회 대상. 게시물과 마찬가지로 소속 채널 기준으로 멤버십이 대조된다.
- **채널 북마크(Channel Bookmark)**: 채널에 속한 리소스/링크 모음. 소속 채널 기준으로 멤버십이 대조된다.
- **채널 멤버십(Channel Membership)**: 조회를 수행하는 사용자가 컨텐츠가 속한 채널의 멤버인지 여부. 이 판정 결과가 감사 기록 여부를 결정한다.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 게시물·파일·북마크를 반환하는 모든 조회 경로(단건 조회, 목록, 스레드, 검색, ID 일괄 조회, 신고 목록, 고정 목록, 편집 이력, 파일 다운로드/썸네일/미리보기, 북마크 CRUD, 미리보기, 웹소켓 퍼머링크)에서 비멤버 채널 접근이 발생하면 100% 감사 로그에 기록된다.
- **SC-002**: 보안 담당자는 감사 로그에서 단일 필터 조건(비멤버 접근 표시)만으로 특정 사용자·기간의 비멤버 컨텐츠 접근 이력을 모두 찾아낼 수 있다.
- **SC-003**: 채널 멤버의 정상적인 게시물·파일·북마크 접근 흐름에서는 감사 로그 항목 수·형식에 변화가 없다(회귀 없음).
- **SC-004**: 이 기능 반영 전후로 관련 API의 응답 스키마·동작은 동일하게 유지된다(감사 기록은 서버 내부 로그에만 추가되며 API 응답에는 영향을 주지 않는다).

## Assumptions

- okrbest는 기존에 반영된 감사 로그 인프라(감사 이벤트 상수, 레벨, 파라미터 부착 방식)를 그대로 재사용하며, 이번 기능은 그 위에 이벤트·파라미터를 추가하는 확장이다.
- 대상 범위는 upstream 커밋 `b5a816a`가 실제로 다루는 전체 범위(게시물, 파일, 채널 북마크 관련 REST API 조회/쓰기 엔드포인트, 웹소켓을 통한 퍼머링크 미리보기 이벤트, 알림 생성·ack 과정에서의 게시물 참조)와 일치시킨다. 게시물 생성/수정/삭제 등 기존에 이미 감사되고 있는 쓰기 작업 자체의 감사 방식(성공/실패 판정 등)은 변경하지 않고, 그 위에 "비멤버 접근" 파라미터만 추가한다.
- "비멤버 접근" 판정은 세션 시점의 실제 채널 멤버십 여부를 기준으로 하며, 시스템 관리자 권한 등으로 접근이 허용된 경우도 멤버십 사실 자체는 별도로 기록한다(권한 판정과 감사 기록은 별개 관심사).
- 별도의 설정(feature flag)으로 켜고 끌 필요 없이 기본적으로 항상 동작하는 것으로 가정한다(원본 upstream 구현과 동일한 전제).
- 이 기능은 okrbest가 이미 반영한 Recap 감사 로깅, Desktop 앱 외부 인증 감사 로깅 등 기존 감사 기능과 병행 동작하며 서로 배타적이지 않다.
