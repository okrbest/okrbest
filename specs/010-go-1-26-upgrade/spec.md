# 기능 명세: Go 1.26.2 툴체인 이행

**기능 브랜치**: `010-go-1-26-upgrade`

**작성일**: 2026-08-25

**상태**: 초안

**입력**: 사용자 설명: "Go 1.26.2 툴체인 이행 — upstream e3fbf871(MM-68149, #36418)을 okrbest 트리 전체에 적용. 버전 핀, NewPointer→new 치환, 헬퍼·reflect API 정리, JPEG 픽스처 재생성, CI 신규 잡 check-go-fix, golangci-lint 호환 확인."

## 배경

okrbest 서버는 Go 1.25.9를 목표로 한다(`server/.go-version`, go.mod 4개). upstream은 2026-05-12에 1.26.2로 올렸고(`e3fbf871`), 그 이후 upstream 코드는 Go 1.26 문법을 전제로 쓴다. 우리가 툴체인을 올리지 않으면 앞으로 들어올 upstream 커밋이 컴파일되지 않는다.

이 작업을 upstream 커밋의 단순 반영이 아니라 별도 명세로 분리한 이유는 **작업량의 절반이 upstream diff 바깥에 있기 때문**이다. upstream diff는 자기네 트리의 `model.NewPointer` 호출 3406곳을 치환하지만, okrbest 트리의 호출은 **4678곳**이다. 차이인 약 1200곳은 알림 히스토리·조직 역할·직위 등 okrbest 자체 코드이고, upstream diff에는 존재하지 않는다. JPEG 픽스처도 마찬가지로 우리 트리에서 다시 만들어야 한다.

이미 드러난 증상이 있다. 2026-08-25 sync에서 `bbbfc019`(이미지 라이브러리 교체)를 반영한 직후 `TestGenerateMiniPreviewImage`가 256픽셀 중 42개 불일치로 실패했다. 원인은 코드가 아니라 툴체인이었다 — 개발 머신의 `server/go.work`가 Go 1.26.2를 요구하는데 저장소는 1.25.9를 목표해, 로컬은 1.26의 새 `image/jpeg` 인코더로, CI는 1.25의 인코더로 같은 픽스처를 검증한다. 이 이행이 그 어긋남을 없앤다.

## 사용자 시나리오 및 테스트 *(필수)*

### 사용자 스토리 1 - 개발자가 upstream 커밋을 계속 반영할 수 있다 (우선순위: P1)

`/speckit-sync`로 upstream 커밋을 반영하는 개발자가, Go 1.26 문법(`new(x)` 초기값 형태)을 쓰는 커밋을 만나도 컴파일 실패 없이 처리한다. 지금은 툴체인이 1.25.9라 그런 커밋이 도착하는 즉시 빌드가 깨진다.

**우선순위인 이유**: 미반영 목록이 660건 넘게 쌓여 있고 그중 상당수가 이 커밋 이후 시점이다. 툴체인을 올리지 않으면 sync 작업 자체가 특정 지점에서 멈춘다. 다른 모든 항목보다 앞선다.

**독립 테스트**: 버전 핀만 올린 상태에서 `new(x)` 형태를 쓰는 코드를 한 곳 작성하고 `go build ./...`가 통과하는지 확인한다. 통과하면 이 스토리는 그것만으로 가치를 낸다.

**인수 시나리오**:

1. **Given** 저장소가 Go 1.26.2를 목표로 한다, **When** `go build ./...`를 실행한다, **Then** 서버 전체가 오류 없이 빌드된다.
2. **Given** Go 1.26 전용 문법을 쓰는 코드가 있다, **When** 빌드한다, **Then** 문법 오류가 발생하지 않는다.
3. **Given** 저장소 목표 버전과 개발 머신 툴체인이 모두 1.26.2다, **When** 이미지 픽스처 테스트를 실행한다, **Then** 로컬과 CI가 같은 결과를 낸다.

---

### 사용자 스토리 2 - 이미지 픽스처 테스트가 툴체인 변경에 흔들리지 않는다 (우선순위: P2)

이미지 미리보기·썸네일 테스트가 툴체인 패치 버전이 바뀔 때마다 1픽셀 차이로 실패하지 않는다. 실패했을 때는 개발자가 정해진 절차로 픽스처를 다시 만들 수 있다.

**우선순위인 이유**: Go 1.26 인코더로 바뀌면 기존 픽스처 23개가 전부 불일치한다. 픽스처를 새로 만들지 않으면 P1을 끝내도 테스트가 빨간 상태로 남는다. 또 허용오차 비교를 함께 넣지 않으면 다음 툴체인 상승 때 같은 일을 반복한다.

**독립 테스트**: 픽스처 재생성 후 이미지 패키지 테스트 전체를 실행해 통과하는지 확인하고, 픽스처 갱신 절차를 한 번 실행해 파일이 갱신되는지 확인한다.

**인수 시나리오**:

1. **Given** 툴체인이 1.26.2이고 픽스처가 재생성됐다, **When** 이미지 패키지 테스트를 실행한다, **Then** 전부 통과한다.
2. **Given** 픽스처가 실제 출력과 미세하게 어긋난다, **When** 개발자가 픽스처 갱신 절차를 실행한다, **Then** 픽스처 파일이 실제 출력으로 갱신되고 이후 테스트가 통과한다.
3. **Given** 향후 툴체인 패치 버전이 올라 인코더 출력이 픽셀 단위로 미세하게 달라진다, **When** 테스트를 실행한다, **Then** 허용오차 안이면 통과한다.

---

### 사용자 스토리 3 - 포인터 헬퍼 표기가 트리 전체에서 일관된다 (우선순위: P3)

okrbest 자체 코드를 포함한 저장소 전체가 같은 포인터 생성 표기를 쓴다. 코드 리뷰에서 "여기는 왜 표기가 다른가"를 따질 일이 없고, 자동 검사가 그 일관성을 지킨다.

**우선순위인 이유**: 기능적으로는 P1·P2가 끝나면 동작한다. 다만 일관성 정리를 미루면 이후 upstream 커밋을 반영할 때마다 두 표기가 섞인 파일에서 충돌이 늘고, 자동 검사를 도입할 수 없다.

**독립 테스트**: 저장소 전체에 자동 정리를 실행한 뒤 변경이 남지 않는지 확인한다. 변경이 없으면 일관성이 확보된 것이다.

**인수 시나리오**:

1. **Given** 자동 정리가 트리 전체에 적용됐다, **When** 자동 정리를 다시 실행한다, **Then** 변경 파일이 발생하지 않는다.
2. **Given** 누군가 옛 표기로 코드를 추가한 변경을 올린다, **When** CI가 돈다, **Then** 검사가 실패하고 무엇을 실행해야 하는지 알려준다.

---

### 엣지 케이스

- 저장소 목표 버전과 개발 머신에 설치된 툴체인이 다르면 어떻게 되는가? 개발 머신의 `server/go.work`는 추적되지 않는 로컬 파일이라 사람마다 다를 수 있다. 이행 후 목표 버전이 1.26.2가 되므로 현재 어긋남은 해소되지만, 절차 문서에 목표 버전과 확인 방법을 남겨야 한다.
- 자동 정리가 okrbest 자체 코드의 의도를 바꾸는 곳이 있는가? 포인터 생성 표기 치환은 의미 보존 변환이지만, 자체 코드 약 1200곳은 upstream 검토를 거치지 않았다. 자동 정리 결과를 사람이 표본 검토해야 한다.
- 정적 분석 도구가 새 툴체인을 지원하지 않으면? 지원 여부를 먼저 확인하고, 미지원이면 도구 버전 상승이 이 작업의 선행 과제가 된다.
- 이행 중 다른 작업이 병행되면? 이 작업은 거의 모든 Go 파일을 건드리므로, 동시에 열린 변경은 대규모 충돌을 겪는다. 이행 기간에는 다른 Go 변경을 병합한 뒤 시작하거나, 이 작업을 먼저 병합해야 한다.
- 제외한 upstream 계보에 속한 파일의 훅은? upstream diff의 충돌 7건 중 2건(`api4/properties_test.go`, `model/view_test.go`)은 우리 트리에 없는 파일이다. 반영 대상이 아니다.

## 요구사항 *(필수)*

### 기능 요구사항

- **FR-001**: 저장소의 Go 목표 버전을 1.25.9에서 1.26.2로 올린다. 대상은 버전 핀 5개 — `server/.go-version`, `server/go.mod`, `server/public/go.mod`, `tools/mattermost-govet/go.mod`, `tools/sharedchannel-test/go.mod`.
- **FR-002**: 서버 전체가 새 툴체인으로 빌드된다. 어떤 패키지도 컴파일 오류를 내지 않는다.
- **FR-003**: 포인터 생성 헬퍼 호출을 Go 1.26 내장 표기로 치환한다. **upstream이 다루지 않는 okrbest 자체 코드까지 포함해** 트리 전체가 대상이다. 현재 호출은 4678곳이고 upstream diff가 덮는 범위는 3406곳이다.
- **FR-004**: 치환이 자동으로 수행되고 재현 가능해야 한다. 사람이 4678곳을 손으로 고치는 방식은 허용하지 않는다.
- **FR-005**: 쓰이지 않게 된 지역 포인터 헬퍼를 제거한다 — `bToP` 37곳, `boolPtr` 4곳.
- **FR-006**: Go 1.26에서 제거된 리플렉션 별칭 사용처를 현재 이름으로 바꾼다(`reflect.Ptr` 19곳). 구조체 필드·메서드 순회도 새 순회 표기로 바꾼다.
- **FR-007**: 이미지 픽스처 23개를 새 툴체인 출력으로 재생성한다. 대상은 `server/tests/`의 방향 보정 미리보기·썸네일 18개, TIFF 2개, GIF 2개, 미니 미리보기 1개.
- **FR-008**: 이미지 비교를 바이트 동일성에서 **허용오차 픽셀 비교**로 바꾼다. 툴체인 패치 버전 상승에 따른 미세한 인코더 출력 변화를 테스트가 스스로 흡수해야 한다.
- **FR-009**: 픽스처 갱신 절차를 제공한다. 개발자가 정해진 한 가지 방법으로 픽스처를 실제 출력으로 덮어쓸 수 있어야 하고, 그 방법이 문서에 남아야 한다.
- **FR-010**: 포인터 표기 일관성을 CI가 자동으로 검사한다. 옛 표기가 남으면 검사가 실패하고, 실패 메시지가 개발자에게 실행할 명령을 알려준다.
- **FR-011**: 정적 분석 도구(golangci-lint, 현재 v2.11.4)가 Go 1.26.2를 지원하는지 확인하고, 미지원이면 지원 버전으로 올린다. `make check-style`이 통과해야 한다.
- **FR-012**: 프로젝트 규범 문서의 Go 버전 표기를 갱신한다. `.specify/memory/constitution.md`가 현재 **Go 1.24.6**을 명시하고 있어 실제(1.25.9)와 이미 어긋나 있다 — 두 곳(원칙 I, 기술 스택 절)을 1.26.2로 맞춘다.
- **FR-013**: upstream 커밋의 충돌 지점 중 우리 트리에 존재하지 않는 파일(`api4/properties_test.go`, `model/view_test.go`)의 변경은 반영하지 않는다. 실질 충돌 5건(`api4/post_test.go`, `app/channel_test.go`, `storetest/post_store.go`, `model/config.go`, `model/property_field_test.go`)은 okrbest 쪽 내용을 보존하며 해소한다.
- **FR-014**: 완료 커밋 본문에 upstream 참조를 넣어 미반영 목록에서 자동 차감되게 한다 — `Upstream: https://github.com/mattermost/mattermost/commit/e3fbf8711f73ac1266ebc943f88999175c2594ef`.

### 핵심 산출물

- **버전 핀**: 저장소가 목표하는 Go 버전을 선언하는 5개 파일. CI가 이 값을 읽어 빌드 이미지를 고른다.
- **포인터 표기**: 값 하나를 받아 그 포인터를 돌려주는 표기. 기존에는 프로젝트 헬퍼 함수였고, Go 1.26부터 언어 내장 기능으로 대체된다.
- **이미지 픽스처**: 이미지 변환 결과의 기대값으로 저장소에 체크인된 이진 파일 23개. 인코더가 바뀌면 함께 바뀌어야 한다.
- **일관성 검사**: 옛 표기가 남았는지 CI에서 판정하는 검사. 보호 경로인 워크플로 파일에 추가된다.

## 성공 기준 *(필수)*

### 측정 가능한 결과

- **SC-001**: 서버 전체 빌드가 오류 0건으로 끝난다.
- **SC-002**: 저장소 어디에도 옛 포인터 헬퍼 호출이 남지 않는다 — 자동 정리를 다시 돌렸을 때 변경 파일 **0개**.
- **SC-003**: 이미지 패키지 테스트가 전부 통과한다. 특히 `TestGenerateMiniPreviewImage`가 개발 머신과 CI 양쪽에서 동일하게 통과한다(현재는 로컬에서 42/256 픽셀 불일치로 실패).
- **SC-004**: 품질 게이트가 통과하고 그 출력을 근거로 제시한다 — `make check-style` 지적 **0건**, 서버 테스트 실패 목록이 이행 전 기준선과 **동일**(신규 실패 0건).
- **SC-005**: 옛 표기를 일부러 넣은 변경을 올리면 CI 검사가 **실패**한다(검사가 실제로 작동함을 확인).
- **SC-006**: 개발자가 픽스처 갱신 절차를 문서만 보고 1회 실행해 픽스처를 갱신할 수 있다.
- **SC-007**: 이행 완료 후 미반영 목록에서 해당 upstream 커밋이 자동 차감돼 남은 커밋 수가 1 줄어든다.

## 가정

- 이 작업은 **동작을 바꾸지 않는다**. 포인터 표기 치환과 리플렉션 이름 변경은 의미 보존 변환이고, 픽스처 재생성은 기대값을 새 인코더 출력에 맞추는 것이다. 사용자에게 보이는 기능 변화는 없다.
- 이미지 출력의 미세한 픽셀 차이는 품질 저하가 아니라 인코더 구현 차이로 본다. 두 인코더 모두 같은 품질 설정을 쓴다.
- Go 1.26.2가 배포되어 개발 머신과 CI 빌드 이미지에서 사용 가능하다. 현재 개발 머신에는 이미 설치돼 있다.
- 자동 정리 도구가 트리 전체를 안전하게 처리한다고 보되, okrbest 자체 코드 약 1200곳의 결과는 사람이 표본 검토한다.
- 이행 기간에는 대규모 Go 변경을 병행하지 않는다. 거의 모든 Go 파일을 건드리므로 동시 작업은 충돌 비용이 크다.
- webapp은 이 작업의 범위 밖이다. Go 툴체인만 다룬다.
- 개발 머신의 `server/go.work`는 추적되지 않는 로컬 파일이라 이 작업의 산출물이 아니다. 다만 목표 버전이 1.26.2가 되면서 현재의 어긋남이 자연히 해소된다.

## 의존성

- upstream 커밋 `e3fbf871`(MM-68149, #36418)이 참조 구현이다. 262파일 +4680/-4586 규모이며, 우리는 이를 참고하되 트리 전체 이행을 직접 수행한다.
- 보호 경로 3곳을 건드린다 — `.github/workflows/server-ci.yml`(CODEOWNERS), `server/enterprise/elasticsearch/common/templates.go`, `server/enterprise/elasticsearch/common/indexing_job_test.go`. 병합 시 code owner 리뷰가 필요할 수 있다.
- 제외한 upstream 계보(`48f2fd08` Integrated Boards / property 시스템 v2)에 속한 파일은 우리 트리에 없다. 그 계보 관련 훅은 반영 대상이 아니다.
