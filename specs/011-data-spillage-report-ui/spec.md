# Feature Specification: 신고 메시지 증거 보고서 UI

**Feature Branch**: `011-data-spillage-report-ui`

**Created**: 2026-08-26

**Status**: Draft

**Input**: upstream `f0360a83` (Data spillage report generation UI, #36340)를 okrbest 용어로 재설계한다. `/speckit-sync` 2026-05-18 세션에서 spec 전환 결정. ledger 부록 `spec 전환 커밋` 표 참조.

## 배경

검토자가 신고된 메시지를 **삭제**하면 원문이 사라진다. 되돌릴 수 없다. 지금 okrbest에는 삭제 전에 증거를 남길 수단이 UI에 없다.

서버는 이미 준비돼 있다. `2e5c23dc8b`(upstream `56089922`, #36339 adapt)가 `POST /content_flagging/post/{postId}/report`와 ZIP 조립을 반영했다 — 게시물 본문, 첨부, 편집 이력, `content_review.yaml`, `report_metadata.yaml`. 이번 작업은 그 위에 얹는 웹앱 UI와, 검토자의 처분 결정을 보고서에 남기기 위한 서버 계약 확장이다.

### 용어를 왜 upstream과 다르게 가나

upstream은 `f1b9aa052e`(#35407)에서 Content Flagging을 'Data Spillage Handling'/'Quarantine for Review'로 전면 개명했다. 우리는 그 커밋을 사용자 확인을 거쳐 제외했다. 기본 신고 사유가 'OPSEC concern', 'CUI violation', 'Need-to-know violation' 같은 미국 국방·정보기관 용어로 바뀌는데, okrbest는 일반 협업·OKR 도구라 제품 성격과 맞지 않는다.

그래서 이 기능의 사용자 노출 문자열과 i18n 키는 기존 계열을 그대로 쓴다 — 영문 `Content Flagging`/`Flag message`, 한국어 `콘텐츠 신고`/`신고`/`메시지 유지`/`메시지 삭제`, 키 네임스페이스 `keep_remove_flag_content_modal.*`. upstream의 `keep_remove_quarantined_content_modal.*`를 들이면 우리 `en.json`에 없는 키를 참조해 `defaultMessage`("quarantined for review by")로 폴백하고, 제외 결정이 그 자리에서 무너진다.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 삭제 전에 증거를 확보한다 (Priority: P1)

검토자가 신고된 메시지를 삭제하려 한다. 확인 창에서 증거 보고서를 내려받은 뒤에야 삭제를 확정한다. 보고서에는 원문·첨부·편집 이력과 함께 검토자가 어떤 결정을 내렸는지가 기록된다.

**Why this priority**: 이 기능의 존재 이유다. 삭제는 되돌릴 수 없고 원문이 사라지므로, 증거 확보 없이 삭제하면 사후 감사가 불가능하다. 이것만 구현해도 독립적인 가치가 있다.

**Independent Test**: 신고된 메시지를 삭제 흐름으로 진입해 보고서를 내려받고, ZIP 안에 원문과 검토자 결정(`remove`)이 들어 있는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 검토자가 신고된 메시지의 삭제 확인 창을 열었고 보고서 내려받기가 선택돼 있다, **When** 검토자가 진행을 누른다, **Then** 보고서 생성이 시작되고 완료되면 ZIP 파일이 기기에 내려받아진다.
2. **Given** 보고서 내려받기가 끝났다, **When** 검토자가 삭제를 확정한다, **Then** 메시지가 채널에서 삭제되고 확인 창이 닫힌다.
3. **Given** 검토자가 댓글을 입력했다, **When** 보고서가 생성된다, **Then** 그 댓글이 보고서의 검토 기록에 포함된다.
4. **Given** 보고서가 생성됐다, **When** 검토자가 다시 내려받기를 누른다, **Then** 같은 보고서를 다시 내려받는다.

---

### User Story 2 - 보고서 없이 삭제하려면 한 번 더 확인한다 (Priority: P1)

검토자가 보고서를 받지 않고 삭제하려 한다. 시스템이 그 선택의 결과를 명시하고 한 번 더 확인을 받는다.

**Why this priority**: P1과 짝을 이룬다. 확인 단계가 없으면 검토자가 실수로 증거 없이 삭제하고, 그 뒤에 생성하는 보고서에는 원문이 남지 않는다. 되돌릴 수 없는 손실이다.

**Independent Test**: 보고서 내려받기를 해제하고 삭제를 시도해, 추가 확인 단계가 뜨고 그 문구가 원문 손실을 명시하는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 검토자가 보고서 내려받기를 해제했다, **When** 삭제를 진행한다, **Then** 보고서 없이 진행한다는 별도 확인 단계가 뜬다.
2. **Given** 추가 확인 단계가 떠 있다, **When** 검토자가 뒤로를 누른다, **Then** 처음 화면으로 돌아가고 입력한 댓글이 유지된다.
3. **Given** 검토자가 메시지를 **유지**하려 하고 보고서 내려받기를 해제했다, **When** 진행을 누른다, **Then** 추가 확인 없이 바로 유지 처리된다.

---

### User Story 3 - 생성이 실패해도 막다른 길에 갇히지 않는다 (Priority: P2)

보고서 생성이 실패한다. 검토자는 다시 시도하거나, 실패를 인지한 채 명시적으로 보고서를 포기하고 진행할 수 있다.

**Why this priority**: 실패는 드물지만 발생한다. 실패 화면에서 아무것도 못 하면 검토자가 신고 처리를 끝낼 수 없다. 다만 P1보다는 빈도가 낮다.

**Independent Test**: 보고서 생성을 실패시키고, 재시도·포기·뒤로 세 경로가 모두 동작하는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 보고서 생성이 실패했다, **When** 실패 화면이 뜬다, **Then** 삭제 확정 버튼이 비활성 상태다.
2. **Given** 실패 화면이 떠 있다, **When** 검토자가 다시 시도를 누른다, **Then** 생성이 재시작된다.
3. **Given** 실패 화면이 떠 있다, **When** 검토자가 보고서를 포기하고 진행을 누른다, **Then** User Story 2의 추가 확인 단계를 거친다.

---

### User Story 4 - 처분과 무관하게 보고서만 받는다 (Priority: P3)

검토자가 신고 내역 화면에서 처분 결정 없이 보고서만 내려받는다.

**Why this priority**: 감사·인수인계 상황에서 유용하지만, 처분 흐름 안의 보고서 생성이 먼저다.

**Independent Test**: 신고 내역 행의 보고서 내려받기를 눌러, 처분 상태가 바뀌지 않고 ZIP만 내려받아지는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 검토자가 신고 내역을 보고 있다, **When** 보고서 내려받기를 누른다, **Then** 보고서가 생성되고 내려받아지며 메시지 처분 상태는 변하지 않는다.
2. **Given** 보고서 생성이 진행 중이다, **When** 검토자가 같은 버튼을 다시 누른다, **Then** 중복 요청이 시작되지 않는다.

---

### Edge Cases

- 보고서 생성 중에 검토자가 확인 창을 닫으면 어떻게 되나? → 진행 중인 요청을 취소한다. 부분 파일을 내려받지 않는다.
- 보고서 생성 중에 검토자가 뒤로를 누르면? → 요청을 취소하고 처음 화면으로 돌아간다. 입력한 댓글은 유지한다.
- 댓글이 필수로 설정된 상태에서 댓글이 비어 있으면? → 진행을 막고 오류 문구를 보여준다. 보고서 생성을 시작하지 않는다.
- 같은 메시지에 대해 보고서를 여러 번 생성하면? → 매번 새 ZIP을 만든다. 생성 시점의 상태를 담는다.
- 검토자가 처분 확정 직전에 권한을 잃으면? → 서버가 거부하고, 확인 창은 오류를 표시한 채 열려 있다.
- 첨부가 매우 크거나 편집 이력이 길면? → 생성이 오래 걸린다. 진행 중임을 계속 표시하고 사용자가 포기할 수 있게 한다.

## Requirements *(mandatory)*

### Functional Requirements

**보고서 생성과 내려받기**

- **FR-001**: 시스템은 신고된 메시지의 처분 확인 창에서 증거 보고서를 생성하고 검토자 기기로 내려받아야 한다.
- **FR-002**: 시스템은 보고서 생성 진행 상태를 검토자에게 계속 표시해야 한다.
- **FR-003**: 시스템은 생성이 끝난 보고서를 검토자가 다시 내려받을 수 있게 해야 한다.
- **FR-004**: 시스템은 검토자가 입력한 댓글을 보고서의 검토 기록에 포함해야 한다.
- **FR-005**: 시스템은 검토자의 처분 결정(유지 또는 삭제)과 결정 주체(사용자 ID·사용자명)를 보고서의 검토 기록에 남겨야 한다.

**처분 흐름의 안전장치**

- **FR-006**: 시스템은 보고서 없이 **삭제**하려는 검토자에게 별도 확인 단계를 거치게 해야 한다.
- **FR-007**: 그 확인 문구는 이후 생성하는 보고서에 원문이 담기지 않는다는 사실을 명시해야 한다.
- **FR-008**: 시스템은 보고서 없이 **유지**하려는 경우에는 추가 확인을 요구하지 않아야 한다. 유지는 되돌릴 수 있다.
- **FR-009**: 보고서 생성이 실패하면 시스템은 처분 확정 버튼을 비활성화해야 한다. 검토자가 실패를 인지하지 못한 채 확정하는 것을 막는다.
- **FR-010**: 실패 화면에서 검토자는 재시도, 보고서 포기 후 진행, 처음 화면으로 돌아가기 중 하나를 선택할 수 있어야 한다. 포기 후 진행은 FR-006의 확인 단계를 거친다.
- **FR-011**: 검토자가 각 단계에서 처음 화면으로 돌아가면 시스템은 입력한 댓글을 유지해야 한다.

**요청 취소**

- **FR-012**: 보고서 생성 중에 검토자가 창을 닫거나 뒤로 이동하면 시스템은 진행 중인 요청을 취소해야 한다.
- **FR-013**: 취소된 요청의 결과는 화면에 반영하지 않아야 한다. 부분 파일을 내려받지 않는다.

**독립 내려받기**

- **FR-014**: 시스템은 신고 내역 화면에서 처분과 무관하게 보고서만 내려받는 수단을 제공해야 한다.
- **FR-015**: 독립 내려받기는 검토자의 처분 결정을 기록하지 않아야 한다. 처분하지 않았기 때문이다.
- **FR-016**: 독립 내려받기가 진행 중이면 시스템은 중복 요청을 시작하지 않아야 한다.

**접근성**

- **FR-017**: 시스템은 파괴적 동작(삭제 확정, 보고서 포기)에 기본 포커스를 두지 않아야 한다. Enter 키만 눌러서 되돌릴 수 없는 처분이 확정되면 안 된다.
- **FR-018**: 각 단계 전환 시 화면 제목이 현재 단계를 나타내야 한다.

**용어와 i18n**

- **FR-019**: 이 기능이 추가하는 모든 사용자 노출 문자열은 `콘텐츠 신고`/`신고`/`메시지 유지`/`메시지 삭제` 계열 용어를 써야 한다. `격리(quarantine)`, `데이터 유출(data spillage)` 계열 용어를 사용자에게 노출하지 않는다.
- **FR-020**: 이 기능이 추가하는 i18n 키는 `keep_remove_flag_content_modal.*` 네임스페이스를 써야 한다.
- **FR-021**: 추가하는 모든 문자열은 `en.json`과 `ko.json`을 같은 변경에서 함께 채워야 한다 (constitution 원칙 V).
- **FR-022**: 시스템은 기존 서버 문자열 `"@%s generated a report for the quarantined message."`(`server/channels/app/content_flagging_report.go`)를 우리 용어로 고쳐야 한다. `#36339` adapt 때 딸려 들어온 용어 오염이다.

**권한과 라이선스**

- **FR-023**: 보고서 생성은 해당 팀의 콘텐츠 검토자만 수행할 수 있어야 한다. 기존 신고 처리 권한 규칙을 따른다.
- **FR-024**: 라이선스·기능 설정으로 콘텐츠 신고가 꺼져 있으면 이 기능의 진입점을 노출하지 않아야 한다. 기존 게이트(`MinimumEnterpriseAdvancedLicense`)를 그대로 따르고, 이 기능만을 위한 별도 완화 경로를 만들지 않는다.

**보고서 접근 기간**

- **FR-025**: 시스템은 메시지가 삭제된 뒤에도 신고 내역에서 보고서를 내려받을 수 있게 해야 한다. 처분 이력과 검토 기록은 삭제 후에도 감사에 필요하다.
- **FR-026**: 삭제 후 생성한 보고서에는 원문이 담기지 않는다. 시스템은 이 사실을 삭제 전 확인 단계에서 미리 알려야 한다 (FR-007).

### Key Entities

- **증거 보고서**: 신고된 메시지 하나에 대한 ZIP 묶음. 게시물 본문, 첨부 파일, 편집 이력, 검토 기록, 보고서 메타데이터를 담는다. 생성 시점의 상태를 고정한다.
- **검토 기록**: 보고서 안의 항목. 신고자, 검토자, 검토자 댓글, 처분 시각에 더해 이번 작업이 추가하는 **처분 결정**(유지/삭제)과 **결정 주체**(사용자 ID·사용자명)를 담는다.
- **처분 확인 흐름**: 검토자가 유지·삭제를 확정하기까지 거치는 단계 묶음. 입력 → (보고서 없이 진행 확인) → 생성 중 → 생성 완료 → 실패. 각 단계는 검토자가 무엇을 할 수 있는지를 다르게 규정한다.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 검토자는 신고 메시지 처분을 시작해 증거 보고서를 확보하고 처분을 확정하기까지 90초 안에 끝낼 수 있다.
- **SC-002**: 보고서를 받지 않고 삭제하려는 시도 중 100%가 추가 확인 단계를 거친다. 확인 없이 삭제되는 경로는 0건이다.
- **SC-003**: 보고서 생성이 실패한 상태에서 처분이 확정되는 경우는 0건이다. 검토자가 실패를 명시적으로 인지하고 선택한 경우만 진행된다.
- **SC-004**: 생성 중 창을 닫은 요청의 100%가 취소되고, 부분 파일이 기기에 남지 않는다.
- **SC-005**: 이 기능이 추가한 사용자 노출 문자열 중 `격리`·`데이터 유출` 계열 용어를 쓰는 것은 0건이다.
- **SC-006**: 이 기능이 추가한 i18n 키 중 `ko.json` 번역이 비어 있는 것은 0건이다.
- **SC-007**: 삭제된 메시지에 대해 사후 감사가 필요할 때, 검토자가 남긴 보고서로 원문·첨부·편집 이력·처분 결정·결정 주체를 모두 확인할 수 있다.
- **SC-008**: 메시지가 삭제된 뒤에도 검토자는 신고 내역에서 처분 결정과 검토 기록을 담은 보고서를 받을 수 있다.

## Assumptions

- 서버의 보고서 생성 API와 ZIP 조립은 이미 동작한다 (`2e5c23dc8b`). 이번 작업은 여기에 처분 결정 기록을 더하고 웹앱 UI를 얹는다.
- upstream `f0360a83`의 서버 쪽 6파일은 우리 트리에 그대로 적용된다. `git apply --check`로 확인했다. 이 부분은 계약을 새로 설계하지 않고 upstream 것을 따른다.
- 웹앱 클라이언트에는 보고서 생성 호출이 없다. Go 클라이언트에만 있다. 새로 만든다.
- 보고서 파일 이름은 기존 `flagged-post-` 계열을 유지한다. 이미 우리 용어와 맞는다.
- 처분 흐름의 단계 구성은 upstream 구조를 따른다. 검증된 흐름이고, 다르게 갈 이유가 없다. 다만 문구와 키는 우리 것을 쓴다.
- 이 기능은 웹앱 전용이다. 모바일 앱은 okrbest가 포크하지 않았다.
- 보고서는 생성 시점에 즉시 내려받는다. 서버가 보고서를 보관하지 않는다.
- 라이선스 게이트를 유지하기로 결정했다(FR-024). 결과로 이 기능은 Enterprise Advanced 라이선스가 없는 배포에서는 화면에 나타나지 않는다. 이를 감수하고 upstream과의 코드 정렬을 택했다. 게이트 정책 자체를 바꾸는 일은 이 명세의 범위 밖이며, 콘텐츠 신고 전체에 걸친 별도 과제다.
- 삭제 후에도 보고서 내려받기를 허용하기로 결정했다(FR-025). 원문이 빠진 보고서가 나올 수 있고, 이는 삭제 전 확인 문구(FR-007)로 사전에 알리는 것으로 방어한다. 파일 자체에 원문 부재를 표시하는 일은 범위 밖이다.

## Dependencies

- `POST /content_flagging/post/{postId}/report` — 이미 존재. `action` 파라미터를 추가한다.
- 콘텐츠 신고 기능 전반(설정, 검토자 지정, 신고 처리 흐름) — 이미 존재.
- upstream `f0360a83` — 참조 구현. 서버 부분은 그대로, UI는 용어를 바꿔 재작성한다.
- 제외 커밋 `f1b9aa052e` — 이 명세의 용어 제약이 여기서 나온다. 되돌리면 FR-019·FR-020이 무효가 된다.

## Out of Scope

- 서버가 보고서를 보관하거나 재발급하는 기능.
- 보고서 형식 변경(ZIP 구성, YAML 스키마). 기존 것을 그대로 쓴다.
- 모바일 앱 대응.
- 콘텐츠 신고 기능 자체의 다른 개선.
- upstream `f1b9aa052e` 개명 재검토.
