# Phase 0 조사: 이미지 프리뷰 확대·이동 조작 확장

**대상 명세**: [spec.md](./spec.md)
**작성일**: 2026-09-03

명세가 plan으로 미뤄 둔 결정 하나와, 조사하며 드러난 사실 넷을 정리한다.

## 결정 1 — 구현 모델은 현재의 스크롤 방식을 유지한다

### Decision

**현재 방식(이미지의 실제 width/height를 바꾸고 컨테이너 스크롤로 넘침을 처리)을 유지한다.** upstream의 표시 변형(`transform: translate() scale()`) + 넘침 잘라내기(`overflow: hidden`)로 옮기지 않는다.

### Rationale

**첫째, 지켜야 할 동작 넷이 전부 스크롤 방식 위에 서 있다.**

명세 FR-019~022가 요구하는 보존 동작과 현재 구현의 의존 관계:

| 보존 동작 | 지금 무엇에 기대나 |
|---|---|
| 맞춤 배율 자동 축소 (FR-019) | `container.clientWidth / naturalWidth`로 맞춤 비율 계산 — 실제 크기 기준 |
| 리셋이 맞춤 배율로 (FR-020) | `fitScale` 기록값, 위와 같은 기준 |
| 배경 클릭 닫기 (FR-021) | 감싸는 `<div>`가 클릭 대상, `e.currentTarget === e.target` 판별 |
| 확대 컨트롤 노출 조건 (FR-022) | 파일 형식 분기, 모델과 무관 |

표시 변형으로 옮기면 앞의 셋을 변형 좌표계에서 다시 만들고 다시 검증해야 한다. 이번 작업의 목적은 조작 수단 셋을 더하는 것이지 잘 도는 코드를 갈아엎는 것이 아니다. 얻는 것에 비해 잃을 수 있는 것이 크다.

**둘째, 성능 우려는 설계로 피할 수 있다.**

표시 변형을 택하는 가장 큰 이유는 GPU 합성이라 부드럽다는 것이다. 크기를 바꾸면 매 프레임 레이아웃을 다시 계산해 끊길 수 있다(SC-006 위험). 그런데 이번 조작 셋을 뜯어보면 실제 위험은 작다.

- **끌기**: `scrollLeft`/`scrollTop`만 바꾼다. 레이아웃 재계산이 없다. 리액트 상태를 거치지 않고 ref로 직접 쓰면 재렌더도 없다.
- **휠**: 배율이 단계로 변한다. 연속 조작이라도 rAF로 한 프레임에 한 번만 반영하면 된다.
- **되읽기 회피가 핵심이다.** 커서 기준점을 맞추려면 보통 크기를 바꾼 뒤 `scrollWidth`를 읽어야 하는데, 그 되읽기가 강제 동기 레이아웃을 일으켜 끊김을 만든다. **우리는 되읽을 필요가 없다.** `scaledWidth = baseSize.width × zoomRatio`를 이미 우리가 계산하고 있어서, 바뀐 뒤의 스크롤 목표값을 식으로 바로 구할 수 있다(아래 결정 2).

**셋째, 스크롤바라는 기존 수단이 남는다.** 끌기를 모르는 사용자도 지금처럼 이동할 수 있다. 잘라내기로 옮기면 스크롤바가 사라져 끌기를 발견하지 못한 사용자는 이동 수단을 잃는다.

**넷째, 이름 충돌이 없다.** `image_preview--zoomed`가 우리 쪽에서 "스크롤 켜기"를 뜻한다. 표시 변형으로 옮기면 upstream에서 이 이름이 "전환 효과 적용"을 뜻해 같은 이름에 다른 뜻이 겹친다. 모델을 유지하면 이 문제가 아예 생기지 않는다.

**다섯째, 스냅샷 파손이 최소다.** 감싸는 요소가 `<div>` 그대로라 기존 스냅샷 5건 중 마크업 때문에 깨지는 것이 없다.

### Alternatives considered

**표시 변형으로 이행 (upstream 방식)** — 기각.
얻는 것은 GPU 합성과 upstream 정합이다. 그런데 이 영역은 이미 영구히 갈라져 있다 — 우리는 맞춤 배율과 배경 클릭 닫기를 유지하고 upstream은 둘 다 없다. 정합을 맞춰도 절반이라 이후 upstream 커밋이 그대로 붙지 않는다. GPU 합성은 위에서 본 대로 설계로 대체할 수 있다. 잃는 것(보존 동작 셋 재구현, 스크롤바 어포던스, 스냅샷 전면 갱신)이 더 크다.

**혼합 — 기본 배치는 실제 크기, 확대분만 표시 변형** — 기각.
두 좌표계를 동시에 관리해야 해 가장 복잡하다. 맞춤 배율과 확대 배율이 서로 다른 축에서 움직여 경계 상황(맞춤 배율 근처)에서 어긋나기 쉽다. 얻는 부드러움에 비해 이해하고 검증할 비용이 크다.

## 결정 2 — 커서 기준 확대는 되읽기 없이 식으로 계산한다

### Decision

크기를 바꾼 뒤 DOM을 되읽지 않고, 바뀐 뒤의 스크롤 목표값을 식으로 구해 같은 프레임에 적용한다.

커서가 가리키던 이미지 위의 점이 화면상 제자리에 남으려면:

```
newScroll = (oldScroll + cursorOffsetInViewport) × (newRatio / oldRatio) − cursorOffsetInViewport
```

- `cursorOffsetInViewport`: 컨테이너 왼쪽(위쪽) 모서리에서 커서까지의 거리
- `oldScroll`: 바꾸기 전 `scrollLeft`(`scrollTop`)
- `newRatio / oldRatio`: 배율 변화 비

가로·세로에 같은 식을 각각 적용하고, 결과를 `[0, scaledSize − clientSize]`로 자른다. `scaledSize`는 `baseSize × newRatio`로 이미 알고 있어 되읽기가 필요 없다.

### Rationale

되읽기(`scrollWidth`, `getBoundingClientRect`)를 크기 변경 직후에 하면 브라우저가 레이아웃을 즉시 계산하도록 강제한다. 휠처럼 연속으로 들어오는 입력에서 이것이 끊김의 주된 원인이다. 우리는 원본 크기(`baseSize`)와 배율을 모두 들고 있어 결과를 예측할 수 있으므로 되읽을 이유가 없다.

### Alternatives considered

- **바꾼 뒤 `scrollWidth`를 읽어 보정** — 기각. 정확하지만 매 입력마다 강제 레이아웃을 부른다.
- **`ResizeObserver`로 크기 변경을 감지해 그때 보정** — 기각. 한 프레임 늦게 반영돼 커서 아래 지점이 흔들린다.

## 결정 3 — 끌기와 클릭은 이동 거리로 가른다

### Decision

`mousedown` 지점을 기록하고, `mouseup`까지 움직인 거리가 임계값(5px)을 넘으면 그 직후의 `click`을 무시한다.

### Rationale

명세 FR-005와 FR-021이 같은 요소 위에서 부딪힌다. 감싸는 `<div>`에 배경 클릭 닫기가 걸려 있고, 끌기도 같은 요소에서 시작한다. 현재 `handleBgClose`는 `e.currentTarget === e.target`으로 이미지 위 클릭만 걸러내는데, **이동을 끝내며 배경 위에서 버튼을 떼면 대상이 배경이라 그 판별을 통과해 모달이 닫힌다.**

거리 임계값은 손떨림으로 생기는 1~2px 이동을 클릭으로 남겨 두면서 의도한 이동을 걸러낸다. 5px은 브라우저·툴킷이 끌기 시작 판정에 흔히 쓰는 값이다.

### Alternatives considered

- **이동 중이면 무조건 클릭 무시** — 기각. 배경을 눌렀다 그 자리에서 떼는 정상 클릭까지 막을 수 있다. 이동 상태 해제 시점이 `click`보다 늦으면 닫기가 아예 죽는다.
- **`mousedown` 대상이 이미지면 클릭 무시** — 기각. 이미지에서 시작해 배경에서 끝나는 이동은 잡지만, 배경에서 시작하는 이동을 못 잡는다.
- **시간 기준(누른 시간이 길면 이동)** — 기각. 천천히 하는 클릭과 빠른 이동을 잘못 가른다.

## 사실 4 — PDF는 이미 분리돼 있다

조사 결과 이미지와 PDF는 서로 다른 컨테이너를 쓴다.

- 이미지: `file-preview-modal__content` (`overflow` 지정 없음)
- PDF: `file-preview-modal__content-scrollable` + `__scrollable` (`overflow: auto`, 별도 높이)

따라서 이미지 쪽 컨테이너를 손봐도 PDF 화면에 번지지 않는다. 명세가 PDF를 범위 밖에 둔 것과 구조가 맞아떨어진다.

**다만 배율 상태는 공유한다.** `file_preview_modal.tsx`가 `this.state.scale[imageIndex]`를 이미지와 PDF에 함께 넘기고, `handleZoomIn`/`Out`/`Reset`도 파일 형식을 가리지 않는다.

→ **키보드 처리기를 모달 수준에 달면 PDF에서도 그냥 동작한다.** 명세는 PDF를 범위 밖에 뒀으므로 파일 형식으로 막는다. 막는 쪽이 코드가 더 든다는 점은 기록해 둔다 — 나중에 PDF에도 열려면 그 조건 한 줄을 지우면 된다. 휠은 사정이 다르다. PDF는 세로 스크롤로 페이지를 넘기므로 휠을 확대에 쓰면 페이지 넘김과 부딪힌다. 휠은 이미지 전용이어야 한다.

## 사실 5 — 이동 위치는 상태로 들고 있어야 한다

명세 FR-017은 배율과 이동 위치를 파일별로 유지하라고 한다.

배율은 이미 `scale: Record<number, number>`로 파일별로 있다. **이동 위치는 없다.** 스크롤 방식에서 이동 위치는 DOM 노드의 `scrollLeft`/`scrollTop`인데, 감싸는 요소는 파일을 넘겨도 같은 노드라 값이 남거나 초기화된다.

현재 동작을 확인해 보면 파일을 넘길 때 `previewUrl`이 바뀌어 `baseSize`가 0으로 되돌고, 그 결과 스크롤이 0으로 초기화된다. 즉 **지금은 파일별 이동 위치가 유지되지 않는다.** FR-017을 채우려면 파일별 이동 위치를 상태로 올려 파일 전환 시 복원해야 한다.

## 사실 6 — 우리 코드에 잠복 버그가 있다

`file_preview_modal.tsx:151`:

```js
if (props.fileInfos.length !== state.prevFileInfosCount) {
    // 배율·맞춤 배율 초기화
}
```

파일 **개수**가 바뀔 때만 초기화한다. 메시지를 수정해 같은 자리의 첨부가 다른 파일로 **교체**되면 개수가 그대로라 이 조건을 타지 않고, 이전 파일의 배율이 새 파일에 그대로 적용된다.

upstream이 같은 문제를 찾아 파일 식별자(파일 id, 없으면 링크) 비교로 고쳤다. 명세 FR-018이 이 요구를 담고 있다. 우리가 자체 구현하며 놓친 지점이라 이번에 함께 고친다.

## 사실 7 — 배율 기준값은 그대로 둔다

명세의 가정대로 현재 값을 유지한다.

| 값 | 현재 | upstream 제안 | 판단 |
|---|---|---|---|
| 기준 배율 | `DEFAULT_SCALE 1.75` | 이미지용 `1.0` 신설 | **유지**. 우리는 `zoomRatio = scale / 1.75`로 계산해 1.0을 받으면 식이 깨진다 |
| 상한 | `MAX_SCALE 3.0` | 이미지용 `2.0` 신설 | **유지**. 실효 확대는 원본의 `3.0 / 1.75 ≈ 1.71`배 |
| 하한 | `MIN_SCALE 0.25` | 같음 | 유지 |
| 단계 | `SCALE_DELTA 0.25` | 같음 | 유지 |

기준 배율을 그대로 두므로 `popover_bar`에 `defaultScale`/`maxScale` prop을 더할 이유도 없다. upstream이 그 prop을 넣은 것은 파일 형식마다 기준값을 다르게 쓰려던 것인데, 우리는 하나로 통일돼 있다.

**주의**: 상한 3.0은 맞춤 배율이 낮은 큰 이미지에서는 충분하지 않을 수 있다. 예를 들어 맞춤 배율이 0.3이면 3.0까지 가도 원본의 1.71배가 상한이라 문제없지만, 상한은 맞춤 배율과 무관한 절대값이라 작은 이미지에서는 금방 닿는다. 이번 범위에서 바꾸지 않되, 실주행에서 답답하면 별도로 다룬다.
