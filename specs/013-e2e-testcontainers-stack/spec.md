# 기능 명세: E2E testcontainers 의존 서비스 스택

**Feature Branch**: `013-e2e-testcontainers-stack`

**Created**: 2026-10-03

**Status**: Draft

**Input**: upstream `a8c2307b` (E2E/Playwright: Add testcontainers to playwright-lib, #37570)을 okrbest에 도입한다. Playwright e2e가 의존 서비스를 컨테이너로 직접 띄우게 하는 테스트 인프라다. upstream 충실 반영을 기준으로 하되 okrbest 환경에 맞춘다.

## 배경

지금 okrbest의 Playwright e2e는 서버와 의존 서비스가 **이미 떠 있다고 가정한다**.
`test_config.ts:33`이 `PW_BASE_URL || 'http://localhost:8065'`를 읽을 뿐, 서버도
Postgres도 메일 서버도 직접 준비하지 않는다. 그래서 테스트를 돌리려면 사람이
`make start-docker`로 compose를 띄우고 `make run-server`로 서버를 올린 상태여야 한다.
준비가 어긋나면 테스트가 깨지고, 깨진 원인이 제품인지 환경인지 구분되지 않는다.

이 기능은 그 가정을 없앤다. 테스트가 자기 의존 서비스를 직접 띄우고, 다 쓰면 거둔다.

**우선순위 근거** — 후속 upstream 커밋 5건이 이 토대에 의존하고 첫 건이 사흘치 뒤다.

## User Scenarios & Testing *(mandatory)*

### User Story 1 — 준비 없이 e2e를 돌린다 (Priority: P1)

개발자가 저장소를 받아 명령 하나를 실행한다. 의존 서비스가 컨테이너로 뜨고,
**okrbest 서버**가 그 위에서 기동하고, e2e 스펙이 그 서버를 상대로 돈다. 개발자는
Postgres를 설치하지도, 메일 서버를 띄우지도, 서버를 따로 실행하지도 않는다.

**이 우선순위인 이유**: 이것만 되면 나머지 없이도 값이 나온다. 사람이 환경을 맞추는
단계가 사라지므로 테스트 실패가 제품 결함을 가리킨다. 그리고 **테스트 대상이 우리
제품이어야 한다는 요건이 여기 들어 있다** — 이게 깨지면 인프라가 들어와도 okrbest를
테스트하지 못한다.

**독립 검증**: 개발 compose와 서버를 모두 내린 상태에서 스모크 스펙 1건을 실행해
통과하면 끝. 다른 스토리는 필요 없다.

**Acceptance Scenarios**:

1. **Given** 개발 compose와 서버가 모두 내려가 있고 Docker 데몬만 돌고 있다, **When** 개발자가 스택 기동 명령으로 e2e 스모크 스펙을 실행한다, **Then** 의존 서비스와 서버가 자동으로 뜨고 스펙이 통과한다.
2. **Given** 스택이 서버를 띄웠다, **When** 테스트가 서버 버전 정보를 조회한다, **Then** 응답이 okrbest 작업 트리에서 빌드한 산출물과 일치한다 (upstream 배포 이미지가 아니다).
3. **Given** 서버 이미지를 지정하지 않았다, **When** 스택을 기동한다, **Then** upstream 기본 이미지로 조용히 넘어가지 않고 멈추며 어떤 이미지를 어떻게 준비하라는지 알린다.
4. **Given** 개발자가 다른 서버 이미지를 쓰려 한다, **When** 환경변수로 이미지를 지정한다, **Then** 스택이 그 이미지로 서버를 띄운다.
5. **Given** Docker 데몬이 꺼져 있다, **When** 스택을 기동한다, **Then** Docker 상태가 원인임을 알리고 멈춘다. 서비스 접속 실패로 위장되지 않는다.

---

### User Story 2 — 스택을 띄워 둔 채로 반복 실행한다 (Priority: P2)

개발자가 스펙을 고치며 여러 번 돌린다. 매 실행마다 컨테이너를 다시 띄우면 기다리는
시간이 테스트 시간을 넘는다. 스택을 한 번 띄워 두고, 테스트만 반복하고, 끝나면 거둔다.

**이 우선순위인 이유**: P1이 되면 테스트는 돌아간다. 이건 돌리는 속도 문제다. 없으면
느려서 안 쓰고, 안 쓰면 P1이 무용지물이 된다.

**독립 검증**: 스택 기동 → 같은 스펙 2회 실행 → 스택 종료. 2회차가 1회차보다 빠르고
두 번 다 통과하면 된다.

**Acceptance Scenarios**:

1. **Given** 스택 기동 명령으로 서비스를 띄워 뒀다, **When** 같은 스펙을 연달아 두 번 실행한다, **Then** 두 실행 모두 통과하고 컨테이너는 재기동되지 않는다.
2. **Given** 스택이 떠 있다, **When** 스택 종료 명령을 실행한다, **Then** 스택이 띄운 컨테이너가 모두 사라지고 개발 compose 컨테이너는 그대로 남는다.
3. **Given** 테스트 실행 중 개발자가 중단 신호를 보낸다, **When** 프로세스가 죽는다, **Then** 스택이 띄운 컨테이너가 남지 않는다.

---

### User Story 3 — 인증·검색·스토리지 의존 테스트가 전용 서비스를 받는다 (Priority: P3)

SSO·LDAP·전문검색·파일 스토리지를 거치는 테스트가 각자 필요한 서비스를 받는다.
SSO 테스트는 ID 공급자를, 검색 테스트는 검색 엔진을, 스토리지 테스트는 오브젝트
스토리지를 받는다.

**이 우선순위인 이유**: 후속 커밋 5건 중 2건(`67c177a4`, `8bfa298a`)이 ID 공급자와
LDAP을 직접 쓴다. 다만 그 커밋들은 2026-09-17 이후라 당장 막지 않는다. P1·P2가
먼저다.

**독립 검증**: 각 서비스를 포함한 스택을 띄워 서비스가 준비 상태에 도달하는지 확인한다.
해당 기능 테스트가 아직 없어도 서비스 기동만으로 검증된다.

**Acceptance Scenarios**:

1. **Given** 스택 구성에 ID 공급자와 LDAP을 포함했다, **When** 스택을 기동한다, **Then** 두 서비스가 준비 상태에 도달하고 미리 정의된 테스트 사용자로 조회가 된다.
2. **Given** 스택 구성에 검색 엔진을 포함했다, **When** 스택을 기동한다, **Then** 엔진이 준비 상태에 도달한다.
3. **Given** 테스트가 특정 서비스를 쓰지 않는다, **When** 그 서비스를 구성에서 뺀다, **Then** 스택은 나머지 서비스만 띄우고 기동 시간이 줄어든다.

---

### Edge Cases

- **Docker가 없거나 데몬이 꺼져 있다** → 알 수 없는 연결 오류가 아니라 Docker 상태가 원인임을 알리고 멈춘다.
- **서버 이미지가 준비되지 않았다** → upstream 기본 이미지로 조용히 대체하지 않는다. 멈추고 준비 방법을 알린다. 가장 위험한 실패 양상이다 — 테스트가 통과하는데 우리 제품을 안 보는 상태가 된다.
- **개발 compose가 이미 돌고 있다** → 호스트 포트를 다투지 않는다. 이 머신에 컨테이너 9개가 가동 중인 상태가 기본 전제다.
- **이미지 내려받기 실패·레이트 리밋** → 어느 이미지가 왜 실패했는지 알린다.
- **네이티브 빌드 실패** (설치 스크립트 실행이 필요한 의존) → 설치 단계에서 드러나고 원인 패키지를 알린다.
- **검색 엔진 이미지 최초 빌드** → Dockerfile 빌드가 필요해 첫 기동이 느리다. 캐시 유무로 기동 시간 기대치가 갈린다.
- **테스트 비정상 종료·타임아웃** → 컨테이너가 남지 않는다. 남으면 다음 실행이 쌓인 잔재와 다툰다.
- **스택이 띄운 서버가 스테일하다** → 서버 코드를 고쳤는데 이미지를 다시 안 만들면 옛 바이너리를 테스트한다. 이미지 재생성 책임이 어디 있는지 분명해야 한다.

## Requirements *(mandatory)*

### Functional Requirements

**테스트 대상 (가장 중요)**

- **FR-001**: 스택이 띄우는 서버는 okrbest 작업 트리에서 만든 산출물이어야 한다. upstream 배포 서버 이미지를 테스트 대상으로 쓰지 않는다.
- **FR-002**: 서버 이미지를 지정하지 않은 채 스택을 기동하면 **실패해야 한다**. upstream 기본값으로 조용히 넘어가는 동작을 금지한다.
- **FR-003**: 서버 이미지는 환경변수로 지정할 수 있어야 한다.
- **FR-004**: okrbest 서버 이미지를 만드는 절차가 문서로 있어야 하고, 그 절차만 따라 US1이 재현되어야 한다.

**스택 수명**

- **FR-005**: 스택은 테스트 실행 전에 의존 서비스를 띄우고 각 서비스가 준비 상태에 도달할 때까지 기다린다. 준비 전에 테스트를 시작하지 않는다.
- **FR-006**: 스택은 테스트가 끝나면 자기가 띄운 컨테이너를 거둔다. 비정상 종료·중단에서도 거둔다.
- **FR-007**: 스택 기동과 종료를 테스트 실행과 분리해 호출할 수 있어야 한다 (반복 실행용).
- **FR-008**: 스택이 거두는 대상은 스택이 띄운 컨테이너로 한정한다. 개발 compose 컨테이너를 건드리지 않는다.

**서비스 구성**

- **FR-009**: 스택은 필요한 서비스만 골라 띄울 수 있어야 한다.
- **FR-010**: 스택은 관계형 DB, 메일 수신, 오브젝트 스토리지, Azure 호환 스토리지, LDAP, ID 공급자, 전문검색 엔진 2종을 띄울 수 있어야 한다.
- **FR-011**: 스택이 할당하는 호스트 포트는 개발 compose가 쓰는 포트와 다투지 않아야 한다.

**실패를 읽을 수 있게**

- **FR-012**: Docker가 없거나 데몬이 꺼져 있으면 그 사실을 원인으로 알리고 멈춘다.
- **FR-013**: 서비스 기동 실패는 어느 서비스가 왜 실패했는지 알린다.

**저장소 규율**

- **FR-014**: 신규 npm 의존과 `package-lock.json`을 같은 변경에서 함께 커밋한다 (원칙 II).
- **FR-015**: 설치 스크립트 실행을 허용하는 패키지를 명시적 목록으로 제한한다. 전체 허용을 금지한다.
- **FR-016**: PR이 트리거하는 e2e 게이트(타입 검사·린트·포맷)가 기준선 대비 신규 실패 없이 통과해야 한다.
- **FR-017**: `Copyright (c) 2015-present Mattermost, Inc.` 헤더를 유지한다 (원칙 IV).
- **FR-018**: 구현 완료 커밋 본문에 `Upstream: https://github.com/mattermost/mattermost/commit/a8c2307bee9bd60a3a0f72a658f32599b44cab0b`를 넣는다. 이게 없으면 미반영 목록에서 자동 차감되지 않는다.

### Key Entities

- **서비스 스택**: 한 테스트 실행이 쓰는 컨테이너 묶음. 구성(어느 서비스를 띄울지), 수명(언제 뜨고 언제 거둘지), 접속 정보(테스트가 각 서비스에 닿는 주소)를 갖는다.
- **서비스 컨테이너**: 스택을 이루는 단위. 이미지, 준비 판정 조건, 테스트에 넘길 접속 정보를 갖는다.
- **서버 이미지**: 테스트 대상 okrbest 서버를 담은 이미지. **이 명세에서 가장 민감한 값이다** — 잘못되면 테스트가 통과하면서 우리 제품을 보지 않는다.
- **테스트 설정**: 기존 `test_config.ts`가 갖는 역할. 스택이 할당한 접속 정보를 받아 테스트에 전달한다.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 개발 compose와 서버를 모두 내린 상태에서 문서의 절차만 따라 e2e 스모크 스펙 1건이 통과한다. 사람이 손으로 띄우는 서비스는 0개다.

- **SC-003**: 서버 이미지를 지정하지 않고 기동하면 100% 실패한다. upstream 기본 이미지로 넘어가는 경우는 0건이다.
- **SC-004**: 이미지가 캐시된 상태에서 최소 구성(DB + 메일) 기동이 90초 이내에 준비 상태에 도달한다.
- **SC-005**: 이미지가 캐시된 상태에서 전체 구성 기동이 5분 이내에 준비 상태에 도달한다.
- **SC-006**: 정상 종료·중단·타임아웃 각 경우에서 테스트 후 잔존 컨테이너가 0개다.
- **SC-007**: 개발 compose 컨테이너 9개가 가동 중인 상태에서 스택이 기동한다. 포트 충돌 0건, 종료 후 사라진 개발 compose 컨테이너 0개다.
- **SC-008**: 스택을 띄워 둔 2회차 실행이 1회차보다 빠르다.
- **SC-009**: PR 게이트 실패 목록이 기준선과 같다 (신규 실패 0건).
- **SC-010**: 후속 커밋 `0785004b`를 추가 인프라 작업 없이 반영할 수 있다.

## Assumptions

다섯 결정을 조사 근거로 확정했다. 각 항목에 **근거**와 **재검토 조건**을 붙였다 —
전제가 바뀌면 다시 연다.

### 1. 서버 이미지는 로컬 빌드로 조달한다

`make package-linux-amd64`(`server/build/release.mk:305`)가 tarball을 만들고,
`server/build/Dockerfile`이 `MM_PACKAGE` 인자를 `curl -L $MM_PACKAGE | tar -xvz`로
받는다(31행). 로컬 tarball을 `file://` 경로로 넘겨 okrbest 서버 이미지를 만들 수 있다.
그 이미지를 `SERVER_IMAGE`로 지정한다.

**레지스트리 발행은 범위 밖이다.** 근거 — 우리 PR은 playwright 브라우저 테스트를
돌리지 않는다. PR이 트리거하는 건 `e2e-tests-check.yml`(타입·린트)뿐이고
(`.github/workflows/e2e-tests-check.yml:3-10`), 브라우저 실행은 Argo Events·
`workflow_dispatch` 전용이다. 원격 러너용 이미지를 지금 필요로 하는 경로가 없다.
`build-server-image.yml`은 buildenv(툴체인) 이미지이지 제품 이미지가 아니므로 쓸 수 없다.

**재검토 조건**: Argo Events·`workflow_dispatch` 경로로 실제 테스트를 돌리기로 하면
원격 러너가 당길 이미지가 필요해진다. 그때 레지스트리 발행을 별도 작업으로 연다.

### 2. 서비스 범위는 upstream 전체를 유지한다

`server/build/docker-compose.common.yml`이 이미 `postgres`·`minio`·`azurite`·
`inbucket`·`openldap`·`elasticsearch`·`opensearch`·`redis`·`keycloak`을 정의한다.
검색 엔진은 `Dockerfile.elasticsearch`·`Dockerfile.opensearch`로 빌드하는 것까지
같다(67·86행). 즉 upstream이 띄우는 서비스는 **전부 우리 개발 환경에 이미 있다**.
빼야 할 근거가 없으므로 upstream 충실도를 택한다.

**재검토 조건**: 전체 구성 기동이 SC-005를 못 지키면 기본 구성을 줄이고 서비스별
선택 기동(FR-009)에 맡긴다.

### 3. 신규 의존은 upstream 버전 그대로 받는다

의존 5개를 upstream이 고정한 버전으로 도입한다. 설치 스크립트 허용 목록은 우리
트리에 아직 없는 필드이므로(저장소 전체에서 `allowScripts` 0건) 신규 추가다.
전체 허용이 아니라 패키지별 명시 목록으로 둔다(FR-015).

**재검토 조건**: 네이티브 빌드가 이 머신(darwin arm64)이나 CI에서 실패하면 해당
의존을 쓰는 기능 범위를 줄인다.

### 4. 개발 compose는 남기고 e2e는 testcontainers로 수렴한다

중복을 없애지 않는다. `make start-docker`는 로컬 개발용으로 그대로 두고, e2e만
스택을 쓴다. 둘이 동시에 떠도 되는 근거 — testcontainers는 호스트 포트를 임의
할당하므로 고정 포트를 쓰는 compose와 다투지 않는다. 이 머신에 컨테이너 9개가
가동 중인 상태를 기본 전제로 삼는다(SC-007).

**재검토 조건**: 임의 포트 가정이 깨지는 서비스가 나오면 그 서비스만 따로 다룬다.

### 5. 검증은 로컬 Docker 실주행이다

`.github/workflows/e2e-tests-playwright-template.yml`이 우리 쪽 +471/-243으로
갈라져 있다(`91de3d23` SEC-10179 adapt에서 워크플로 757줄 미반영). **이번 범위에서
그 갈라짐을 메우지 않는다.** upstream 커밋의 워크플로 변경(1파일 +21/-14)은 우리
갈라진 파일에 맞춰 반영하거나 보류하고, 보류하면 `docs/upstream-adapted-divergences.md`에
복원 조건과 함께 남긴다.

종단 판정은 이 머신에서 Docker 실주행으로 한다. Docker가 있고 컨테이너 9개가
돌고 있어 원리상 가능하다.

**재검토 조건**: 로컬 실주행이 막히면 판정 수단이 없어진다. 그때 CI 배선을 범위에 넣는다.

### 그 밖의 전제

- upstream 커밋은 `server/` 코드를 바꾸지 않고 DB 마이그레이션도 없다. 따라서 `server/` 품질 게이트는 이번 범위에서 돌 일이 없다.
- 전체 84파일 중 57파일이 우리 트리에 없다(`lib/src/containers/` 디렉터리 전체가 신규). 즉 대부분이 추가이고 충돌 면적이 작다.
- Keycloak realm export·웹훅 서버 같은 대용량 에셋은 생성물이 아니라 고정 입력이므로 upstream 내용을 그대로 가져온다.
- 후속 커밋 5건의 **테스트 내용**은 이 범위가 아니다. 이 범위는 그 테스트가 올라갈 토대까지다.
- Cypress e2e는 건드리지 않는다.
