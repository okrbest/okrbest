# Feature Specification: 채널별 입장·퇴장 메시지 끄기

**Feature Branch**: `029-join-leave-toggle`

**Created**: 2026-10-15

**Status**: Draft

**Input**: User description: "채널별 입장·퇴장 시스템 메시지 끄기 — upstream mattermost/mattermost 5de31f8e(MM-68909, #37314)를 okrbest 포크에 맞게 반영한다. 채널 관리자가 채널 설정 Configuration 탭에서 이 채널의 입장·퇴장 시스템 메시지를 숨길 수 있다. 메시지는 계속 저장하고 읽기 경로에서만 걸러, 설정을 다시 켜면 다시 보인다. DM·GM 채널은 대상이 아니다. 숨김 채널에서는 join/leave 게시물의 푸시·이메일·실시간 알림을 보내지 않되, '채널에 추가됨' 게시물은 추가된 당사자에게만 알린다. 포크 제약: 자체 사용자 ID 필터(봇 필터)와 함께 동작, 제외한 upstream 계보 문맥 제거, 마이그레이션 보호 경로, 생성물 재생성, 알림 히스토리와의 상호작용 확인." (`/speckit-sync` 2026-10-15 세션에서 spec 전환으로 결정)

## 현재 동작

입장·퇴장 시스템 메시지("○○님이 채널에 참여했습니다", "○○님이 ○○님을 채널에 추가했습니다" 등)는 채널마다 끌 수 없다.
조절 수단은 두 가지뿐이다.

- **사용자별 표시 설정**: 계정 설정 > 고급의 "입장/퇴장 메시지 표시". 보는 사람 한 명에게만 적용된다.
- **시스템 기본값**: 시스템 콘솔의 `EnableJoinLeaveMessageByDefault`. 위 사용자 설정의 초깃값만 정한다.

그래서 공지 채널이나 수백 명이 드나드는 대형 채널은 입장·퇴장 메시지로 대화가 묻힌다. 채널 관리자는 이를 막을 방법이 없다.
이 메시지들은 채널 구성원 전원에게 실시간 알림으로도 퍼진다.

upstream은 이 문제를 `5de31f8e`(2026-09-14)에서 채널 단위 설정으로 풀었다.
우리 포크는 sync 분석 결과 규모(36파일 +2220줄)·DB 스키마 변경·자체 기능과의 겹침 때문에 이 커밋을 바로 받지 않고 spec으로 넘겼다.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 채널 관리자가 입장·퇴장 메시지를 숨긴다 (Priority: P1)

공개·비공개 채널의 관리자가 채널 설정의 Configuration 탭에서 "입장/퇴장 시스템 메시지" 토글을 끈다.
저장하면 그 채널을 보는 **모든 사용자**의 타임라인에서 입장·퇴장 메시지가 사라진다. 각 사용자의 개인 표시 설정과 상관없이 숨겨진다.

**Why this priority**: 기능의 핵심이다. 이것만으로 대형 채널의 소음 문제가 풀린다.

**Independent Test**: 구성원이 여럿 드나든 채널에서 토글을 끄고 저장한 뒤, 다른 구성원 계정으로 채널을 열어 입장·퇴장 메시지가 하나도 보이지 않는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 입장·퇴장 메시지가 섞인 공개 채널이 있고 나는 그 채널의 속성 관리 권한이 있다,
   **When** 채널 설정 > Configuration에서 토글을 끄고 저장한다,
   **Then** 나와 다른 구성원 모두의 타임라인에서 입장·퇴장 메시지가 사라지고 일반 메시지는 그대로 보인다.
2. **Given** 입장·퇴장 메시지가 숨겨진 채널이다,
   **When** 새 구성원이 채널에 참여하거나 누군가 채널을 떠난다,
   **Then** 그 메시지는 어느 구성원의 타임라인에도 나타나지 않는다.
3. **Given** 개인 설정에서 "입장/퇴장 메시지 표시"를 켠 사용자가 있다,
   **When** 그 사용자가 숨김 채널을 연다,
   **Then** 채널 설정이 우선해 입장·퇴장 메시지가 보이지 않는다.
4. **Given** 채널 속성 관리 권한이 없는 일반 구성원이다,
   **When** 채널 설정을 연다,
   **Then** 토글이 보이지 않고, 같은 변경을 직접 요청해도 거부된다.

---

### User Story 2 - 다시 켜면 숨겼던 메시지가 돌아온다 (Priority: P2)

숨김을 해제하면 숨겨져 있던 기간의 입장·퇴장 메시지를 포함해 모든 메시지가 다시 보인다. 메시지는 지워진 적이 없다.

**Why this priority**: 설정이 되돌릴 수 있어야 관리자가 부담 없이 쓴다. 감사·기록 목적의 이력도 보존된다.

**Independent Test**: 숨김 상태에서 구성원 입장을 일으킨 뒤 토글을 다시 켜고, 숨김 기간에 생긴 입장 메시지가 시간 순서대로 나타나는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 숨김 채널에서 숨김 기간 동안 구성원 3명이 입장했다,
   **When** 관리자가 토글을 다시 켜고 저장한다,
   **Then** 세 입장 메시지를 포함해 기존 메시지 전체가 원래 자리에 보인다.
2. **Given** 다른 구성원이 이미 채널을 열어 둔 상태다,
   **When** 관리자가 설정을 바꾼다,
   **Then** 그 구성원은 새로고침 없이 바뀐 설정대로 타임라인을 다시 본다.

---

### User Story 3 - 숨김 채널에서는 입장·퇴장 알림이 울리지 않는다 (Priority: P2)

숨김 채널에서 일어난 입장·퇴장은 구성원에게 푸시·이메일·실시간 알림을 만들지 않는다.
다만 누군가 **다른 사람을 채널에 추가**했을 때, 추가된 당사자는 지금처럼 알림을 받는다. 자신이 어느 채널에 들어갔는지 알 수 있어야 하기 때문이다.

**Why this priority**: 타임라인만 숨기고 알림이 계속 울리면 소음 문제가 반만 풀린다. 다만 타임라인 숨김(US1)이 먼저 있어야 의미가 있다.

**Independent Test**: 숨김 채널에서 (a) 구성원 A가 스스로 입장하고, (b) 관리자가 사용자 B를 추가한다. 기존 구성원 C에게는 아무 알림도 오지 않고, B에게만 추가 알림이 오는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 숨김 채널이다,
   **When** 사용자가 스스로 입장하거나 퇴장한다,
   **Then** 다른 구성원에게 푸시·이메일·실시간 알림이 가지 않는다.
2. **Given** 숨김 채널이다,
   **When** 관리자가 사용자 B를 채널에 추가한다,
   **Then** B는 추가 알림(푸시·이메일·멘션)을 받고, 다른 구성원은 아무것도 받지 않는다.
3. **Given** 숨김 채널이다,
   **When** B가 위 추가 알림을 누르고 채널에 들어간다,
   **Then** 채널은 정상적으로 열린다. 타임라인에서 추가 메시지는 다음 갱신부터 보이지 않는다.

---

### User Story 4 - 우리 자체 필터와 함께 써도 결과가 맞다 (Priority: P2)

okrbest에는 채널 게시물을 특정 사용자의 글로만 좁혀 보는 자체 필터가 있다(봇 메시지 필터 등).
숨김 채널에서 이 필터를 켜도 두 조건이 모두 적용된 결과가 나오고, 스크롤로 이전·이후 글을 불러올 때 빈 화면에 갇히지 않는다.

**Why this priority**: 포크 고유의 회귀 위험이다. upstream 테스트로는 잡히지 않는다.

**Independent Test**: 숨김 채널에서 사용자 필터를 켜고 위아래로 끝까지 스크롤한다. 필터 대상 사용자의 일반 글만 보이고, 로딩이 멈추지 않는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 숨김 채널에서 사용자 필터를 켰다,
   **When** 타임라인을 연다,
   **Then** 필터 대상 사용자의 일반 메시지만 보이고 입장·퇴장 메시지는 보이지 않는다.
2. **Given** 숨김 채널의 한 페이지 분량이 모두 입장·퇴장 메시지다,
   **When** 사용자가 위로 스크롤해 이전 글을 불러온다,
   **Then** 빈 페이지에서 멈추거나 같은 요청을 반복하지 않고, 더 이전의 일반 메시지를 불러오거나 채널 시작에 도달했음을 표시한다.

---

### Edge Cases

- **DM·GM 채널**: 설정 대상이 아니다. 토글이 보이지 않고, 직접 변경 요청을 보내도 거부된다.
- **게스트 입장 메시지**: 게스트 입장·게스트 추가 메시지도 숨김 대상이다. 게스트 추가는 "추가됨" 규칙을 따라 당사자에게 알린다.
- **팀 단위 메시지**: 팀 입장·퇴장·추가·제거 메시지가 채널에 남는 경우(예: 타운스퀘어)에도 같은 규칙을 적용한다.
- **링크·검색·저장으로 접근**: 숨김 채널의 입장·퇴장 메시지는 퍼머링크, 단건 조회, 스레드, 검색 결과, 저장(플래그)한 메시지 목록에서도 보이지 않는다. 고정(pinned) 목록은 upstream도 거르지 않으므로 이 기능의 범위가 아니다.
- **설정 변경 직후의 알림**: 설정을 바꾸는 순간과 거의 동시에 일어난 입장·퇴장은 알림이 한 번 새거나 빠질 수 있다. 타임라인 표시는 항상 현재 설정을 따른다.
- **보관(archived) 채널**: 보관 채널도 설정값을 그대로 따른다.
- **읽지 않음 개수**: 이 기능은 읽지 않음 개수 계산을 바꾸지 않는다(upstream과 같다). 입장·퇴장 10종은 지금도 채널 메시지 수에서 빠지므로 숨겨도 영향이 없다. 게스트 입장·게스트 추가 2종은 메시지 수에 들어가서, 숨김 채널에서 보이지 않는 글 때문에 채널이 읽지 않음으로 표시될 수 있다. upstream과 같은 알려진 차이로 두고, 문제가 되면 별도 과제로 연다(research R9).
- **알림 히스토리(포크 기능)**: 숨김 채널의 입장·퇴장은 알림 히스토리에 남지 않는다. "채널에 추가됨" 멘션은 당사자의 알림 히스토리에 지금처럼 남는다.

## Requirements *(mandatory)*

### Functional Requirements

**설정**

- **FR-001**: 시스템은 공개·비공개 채널마다 "입장/퇴장 시스템 메시지 숨김" 설정을 가져야 한다. 기본값은 "숨기지 않음"이고, 기존 채널도 모두 이 값으로 시작한다.
- **FR-002**: 채널 설정 화면의 Configuration 탭은 채널 속성 관리 권한(공개 채널은 공개 채널 속성 관리, 비공개 채널은 비공개 채널 속성 관리)이 있는 사용자에게만 이 토글을 보여야 한다.
- **FR-003**: 시스템은 권한이 없는 사용자의 설정 변경 요청과, DM·GM 채널에 대한 설정 변경 요청을 거부해야 한다.
- **FR-004**: 설정 변경은 채널 변경 감사 기록에 남아야 한다.

**숨김 대상과 범위**

- **FR-005**: 숨김 대상은 채널·팀 입장, 퇴장, 추가, 제거 메시지와 게스트 입장·게스트 추가 메시지, 모두 12종이다. 그 밖의 시스템 메시지(헤더 변경, 채널 이름 변경 등)는 숨기지 않는다.
- **FR-006**: 숨김 채널에서는 위 메시지를 계속 저장하되, 사용자에게 보이는 모든 조회 경로(채널 타임라인 첫 화면, 이전·이후 불러오기, 마지막 읽은 위치 주변, 변경분 동기화, 단건 조회, 스레드, 퍼머링크, 저장한 메시지 목록, 메시지 검색 결과)에서 빼야 한다.
- **FR-007**: 채널 설정이 사용자 개인의 "입장/퇴장 메시지 표시" 설정보다 우선해야 한다. 숨김 채널에서는 개인 설정과 관계없이 보이지 않는다. 숨김이 아닌 채널에서는 지금처럼 개인 설정을 따른다.
- **FR-008**: 설정을 해제하면 숨겨져 있던 메시지를 포함한 전체 이력이 다시 보여야 한다.

**페이지 이동**

- **FR-009**: 이전·이후 불러오기에서 숨겨진 메시지 때문에 결과가 비어도, 클라이언트는 같은 범위를 반복 요청하지 않아야 한다. 더 이상 메시지가 없으면 그 방향의 끝에 도달한 것으로 처리한다.
- **FR-010**: 페이지 이동의 기준점(이전·이후 위치 계산)은 숨겨진 메시지를 건너뛰어, 보이는 메시지를 가리켜야 한다.

**동기화**

- **FR-011**: 설정이 바뀌면 그 채널을 열어 둔 다른 사용자의 화면이 새로고침 없이 새 설정대로 타임라인을 다시 불러와야 한다.
- **FR-012**: 채널 게시물 응답의 캐시 식별자에 이 설정을 반영해, 설정을 바꾼 뒤 낡은 캐시 결과가 보이지 않아야 한다.

**알림**

- **FR-013**: 숨김 채널에서 추가형이 아닌 입장·퇴장 메시지(스스로 입장·퇴장, 제거 등)는 푸시·이메일·실시간 알림을 만들지 않아야 한다.
- **FR-014**: 숨김 채널에서 추가형 메시지(채널에 추가, 게스트 채널 추가, 팀에 추가)는 추가된 당사자에게만 실시간 이벤트를 보내고, 당사자의 푸시·이메일·멘션 알림을 유지해야 한다. 다른 구성원에게는 아무것도 보내지 않는다.
- **FR-015**: 추가된 당사자의 프로필이 캐시에 아직 없더라도 당사자 알림이 빠지지 않아야 한다.

**포크 호환**

- **FR-016**: 포크의 사용자 ID 필터(특정 사용자 글만 보기, 봇 메시지 필터)와 이 숨김을 함께 적용하면, 두 조건을 모두 만족하는 메시지만 보여야 한다. 둘 중 하나만 켜진 경우의 기존 결과는 바뀌지 않아야 한다.
- **FR-017**: 이 기능은 upstream에서 우리가 받지 않은 기능(관리 카테고리, 보드 뷰, 분류 표시, 채널 속성 값)의 화면 요소나 데이터 필드를 들여오지 않아야 한다.
- **FR-018**: 설정 화면의 문구는 영문과 한국어 카탈로그에 함께 들어가야 한다(영문 2키와 한국어 번역).

### Key Entities

- **채널 설정 — 입장/퇴장 메시지 숨김**: 공개·비공개 채널 하나에 딸린 참/거짓 값. 기본은 거짓. 채널 정보와 함께 클라이언트에 전달되고, 채널 변경 감사 기록에 포함된다.
- **멤버십 시스템 메시지**: 채널·팀 구성원 변화가 남기는 시스템 메시지 12종. "추가형"(채널 추가, 게스트 채널 추가, 팀 추가) 3종은 알림 규칙이 다르다.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 숨김을 켠 채널의 타임라인·퍼머링크·스레드·검색 결과·저장 목록에서 입장·퇴장 메시지가 0건 보인다. 시나리오 테스트에서 12종 각각을 1건 이상 만들어 확인한다.
- **SC-002**: 숨김을 해제한 직후, 숨김 기간에 생긴 입장·퇴장 메시지가 100% 다시 보인다(만든 건수와 보이는 건수가 일치).
- **SC-003**: 숨김 채널에서 스스로 입장·퇴장할 때 다른 구성원이 받는 알림이 0건이다. 사용자를 추가하면 당사자만 알림 1건을 받는다.
- **SC-004**: 다른 사용자가 설정을 바꾸면, 채널을 열어 둔 사용자의 화면이 수동 새로고침 없이 반영된다(실주행 확인).
- **SC-005**: 한 페이지 전체가 숨김 대상인 채널에서 위·아래 끝까지 스크롤해도 같은 범위 요청이 반복되지 않고(요청 수 유한), 끝 도달 상태로 바뀐다.
- **SC-006**: 사용자 필터와 숨김을 함께 켠 채널에서, 필터 대상 사용자의 일반 메시지만 보이고 그 수가 기대값과 일치한다.
- **SC-007**: 숨김을 켜지 않은 채널의 동작(표시·알림·필터 결과)은 반영 전과 같다. 기존 서버·웹앱 테스트가 반영 전 기준선 대비 새 실패 0건이다.
- **SC-008**: 완료 커밋이 반영되면 upstream 미반영 목록에서 `5de31f8e`가 빠진다.

## Assumptions

- 동작은 upstream `5de31f8e`를 기준으로 하고, 포크와 겹치는 부분만 조정한다. upstream 이후 이 기능에 대한 수정 커밋이 나오면 별도 sync로 받는다.
- 권한 모델은 기존 "채널 속성 관리" 권한을 그대로 쓴다. 새 권한은 만들지 않는다.
- 알림 히스토리(포크 #167)는 멘션 알림만 기록하므로, upstream의 알림 규칙(FR-013·FR-014)을 그대로 따르면 위 Edge Cases의 결과가 나온다고 가정한다. plan 단계에서 실제 코드 경로로 확인한다.
- 관리 도구(mmctl)로 이 설정을 바꾸는 기능은 범위 밖이다. upstream 커밋 본문은 mmctl을 언급하지만 실제 변경에는 mmctl 파일이 없다.
- 모바일 앱은 서버가 거른 결과를 받으므로 별도 작업이 없다고 가정한다. 다만 모바일의 실시간 수신 처리는 범위 밖이다.
- 한국어 문구는 이 spec에서 함께 넣는다. sync 예외 규칙(ko는 나중에)을 쓰지 않는다.
- **plan 단계로 넘길 기술 메모**(sync 분석 결과). 요구사항이 아니라 위험 목록이다.
  - 포크 사용자 ID 필터가 upstream과 같은 게시물 조회 함수를 고쳤다. 두 조건을 나란히 넣어야 하고, upstream이 한 조회 함수의 조건 구성 방식을 바꿔 포크 필터 블록이 텍스트 병합 뒤 컴파일에 실패하는 지점이 있다.
  - DB 스키마 변경(채널 테이블 열 추가)과 마이그레이션 목록은 CODEOWNERS 보호 경로라 PR 병합에 관리자 우회가 필요하다. 마이그레이션 번호는 착수 시점의 최신 번호를 다시 확인한다.
  - 저장소 계층 생성물(재시도·타이머 계층, mock)을 다시 만들어야 CI가 통과한다.
  - 제외 계보(관리 카테고리 필드, 보드 뷰 조회 함수, 분류 표시 설정 로직, 채널 속성 값 타입)가 upstream 충돌 문맥에 섞여 있어 걷어내야 한다.
  - 완료 커밋 본문에 `Upstream: https://github.com/mattermost/mattermost/commit/5de31f8e868f61636ee9d556176cd6ab5f956f2b`를 넣는다.
